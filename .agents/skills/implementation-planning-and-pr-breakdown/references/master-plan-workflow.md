# Master plan workflow

Read when writing or materially revising a multi-unit master plan. The parent owns method; repo-docs-system owns shape.

1. Start with the exact Owner outcome and boundary, not mechanisms. Preserve numbered/dated decisions; ask material choices that repository discovery cannot resolve.
2. Inspect current contracts and evidence. Each material assumption names evidence and what invalidates it.
3. Split units by dependency and verification boundary. Each unit has an observable outcome, hard/soft dependencies and a gate to start/enable.
4. State shared invariants with the failure each prevents, rollout compatibility, risks, exclusions and stop/rollback paths.
5. Map every Owner requirement to a unit and each unit to a requirement or repository necessity. Put acceptance close to the unit creating the behavior.
6. Keep execution State in progress, not the master plan. Leave no material choice for an implementor to invent.
7. Self-review with the review skill; lifecycle owns independent review and approval/implementation remain separate.

Only the Owner changes an Owner-controlled goal, decision or scope. When repository reality contradicts the approved master plan, stop affected lower work, report the evidence and smallest correction, then obtain disposition. Hypothesis-only wiring changes do not reopen it.
