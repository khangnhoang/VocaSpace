# D2 — Public Preview interaction design

Status: **frozen pre-implementation design contract; DESIGN=PASS after self-review** against [the implementation plan](./plan.md). D2 was subsequently implemented and independently reviewed `PASS` at `39feb3a`; current delivery evidence belongs to [progress.md](../../progress.md). The baseline observations and design self-review below remain historical, not a claim about the current UI.

## 1. Product grounding and visual direction

Surfaces: teacher authoring (medium/low design latitude), public course discovery (existing public visual language), and focused learner practice (medium latitude). The teacher's job is to choose a small sample of lessons, see the allocation at a glance, and safely change chapter structure. The learner's job is to sample one published lesson and understand that this practice is temporary. Use the existing blue/cyan links and badges, slate structure cards, white panels, and rose destructive controls; no new palette, font, global primitive, or animation system. The signature is a consistent **Preview allocation line** connecting the teacher's count, marked lesson rows, and public Preview badge. Restraint is deliberate: quota and destructive dependencies need clarity more than new decoration.

Current evidence: `CourseStructureWorkspace.tsx` supplies the Structure hierarchy, `ChapterList.tsx` shows per-chapter controls and `TopicManagementSheet.tsx` already opens a topic list. `SettingsTab.tsx` hosts topic settings and delete. `DeleteChapterModal.tsx` uses `ConfirmDialog`. `PublicCourseSyllabus.tsx` renders the temporary first-topic badge; `PublicCourseEnrollmentCard.tsx` carries the enrolled `Tiếp tục học` CTA. `LearningWorkspace.tsx`/`FlashcardStage.tsx` provide the visual card language, but the current callbacks write learning state. Existing `Badge`, `Tooltip`, `Sheet`, `ConfirmDialog`, and button primitives can be composed locally; the quota-resolution dialog needs a feature-local composition because the current generic confirmation has no selection workflow.

External interaction references: [Thinkific free course preview](https://support.thinkific.com/hc/en-us/articles/360030722473-Create-a-Free-Course-Preview) uses a per-lesson setting and highlights sample lessons on the course page; the useful pattern is matching author choice to public syllabus visibility. [Thinkific lesson settings](https://support.thinkific.com/hc/en-us/articles/360038694193-Lesson-Settings) confirms a setting can live beside lesson metadata. [Teachable course setup](https://support.teachable.com/en/articles/11682451-create-and-set-up-your-course) distinguishes published, unpublished, and public preview visibility. VocaSpace retains its own stateless guest Preview, 20% cap, and separate enrollment path; those products' sign-up/progress/payment semantics are not adopted.

## 2. Teacher Structure and topic controls

Desktop hierarchy: title/create chapter → compact recovery warning when suspended → allocation panel → existing course statistics → ordered chapter cards. Mobile: title/create → recovery warning → allocation panel → chapter cards, with statistics below or wrapped without hiding actions. Show the same compact warning on teacher Overview so the problem is visible before entering Structure. The panel reads `Đã chọn xem thử: M/C bài học` and `Còn R lượt chọn` in a valid state; an expandable list shows every **effectively active** marked topic with chapter context, status, jump-to-topic action, and permitted unmark control. The count includes marked draft/pending topics; helper text says `Bài học chưa xuất bản vẫn tính vào giới hạn nhưng chưa mở công khai.` Empty panel: `Chưa chọn bài học xem thử` with a direct `Chọn trong danh sách bài học` action. Do not add a fifth decorative metric card.

For owner/co-owner/editor during moderation-caused suspension, use the existing amber warning/card language (as in `DashboardIssueNotice.tsx`), not a new notification feed. Show `Xem trước bài học đang tạm thời bị vô hiệu hóa`, actual `M/cap`, `Vượt giới hạn {excess} bài học; có thể gỡ ít nhất {excess} nhãn Xem thử`, the causally bound moderation target and `Lý do: {reason}`, and `Điều chỉnh bài học xem thử`. Describe the actor only as `quản trị viên nền tảng`. The CTA focuses the marked-topic allocation list, where the author may select enough active marked topics for one atomic unmark to reach `M <= cap`; show projected `M/cap` and disable confirmation until valid. Valid creation or restoration of enough unmarked active topics may also grow the denominator until the allocation becomes valid, without using this CTA. After any server-confirmed recovery, refresh Overview/Structure and remove the warning automatically. Previewer sees neither warning details nor recovery controls. If the exact causal audit cannot be verified, show a generic private recovery warning/count and flag an operational integrity stop; never display an arbitrary latest reason. This compact surface omits actor identity, event history, timestamps, and before/after audit details so a future course activity surface can own them.

In `TopicManagementSheet`, each readable topic row has one concise Preview status and, for owner/co-owner/editor, a labelled toggle/check control. Owner/co-owner/editor can mark any **active** topic in their course; chapter creator identity does not limit marker management. A draft/pending topic may be marked, with `Chưa công khai` alongside the marker. Removed topics or removed chapters are absent from this active list. At cap, unmarked controls remain discoverable but disabled with the actual `M/C` reason and a link to the marked-topic list for quick unmark; existing marked controls remain enabled for removal. Do not force opening every Builder page. Builder `SettingsTab` repeats the marker state and a compact control in a separate Preview section; it is independent of D1 content-edit `readOnly`, so an eligible marker manager can use it even when content editing is frozen. Refresh the allocation and all visible rows from the server after success; no optimistic quota math presented as committed fact.

Chapter cards show `Chương {position}` from sorted active position, followed by the stored title; do not display raw `order_index` or write numbering into `title`. Owner/co-owner get rename, hide, and reorder on every chapter. Editor gets create and rename/hide only on own recorded chapter, with **no reorder controls**, including on a chapter they created. Other creator's chapter has no edit/hide affordance for an editor; the readable title and topic navigation remain. Previewer has a readable Structure view and no chapter/marker controls. The optional creator cue is omitted for now; authority is expressed by available actions, not an unverified historical attribution. A small `Chương đã ẩn` section supports authorized restore: owner/co-owner see all, editor only own; restoration appends to active order and updates displayed positions after server confirmation.

## 3. Chapter hide dialogs and quota resolution

Opening ordinary hide first checks the D1 pending-child freeze. With an active pending child, disable/stop confirmation and explain `Chương có bài học đang chờ duyệt; hãy xử lý quy trình duyệt trước khi ẩn chương.` No Preview quota resolution or review cancellation is offered. For an otherwise valid hide, request a server projection of current `A`, `M`, cap, internal marker count, and outside marked topics. The dialog identifies the chapter, explains that learners lose access to its lessons/cards/exercises, and states that content is retained for authorized restore. If no Preview marker is inside and projected quota fits, show `Hủy` / `Ẩn chương`. If N internal markers exist and projected quota fits, add `N bài học xem thử trong chương này sẽ tự bỏ nhãn xem thử.` No selection is requested for those N.

If outside markers would exceed the new cap, the same dialog enters an **inline resolution** state. Internal markers are already excluded from the projection and cannot be selected manually. Show `Sau khi ẩn: {projected M}/{projected cap}`; `Cần bỏ thêm {excess} bài học xem thử ở chương khác`. List currently marked active topics outside the target chapter with chapter/status, search or short filter if the list is long, and accessible checkboxes. The projected line updates immediately as selections change; `Ẩn chương và bỏ xem thử` remains disabled until exactly enough or more valid outside markers are selected. A labelled tooltip/help line explains `Bỏ xem thử chỉ tắt quyền xem thử công khai; nội dung và trạng thái xuất bản của bài học không đổi.` The server rechecks projection and role and atomically performs selected outside unmarks + all internal unmarks + chapter hide. Cancel changes nothing.

```text
Ẩn chương “Luyện nghe cơ bản”?
Học viên sẽ không mở được các bài học, thẻ và bài tập trong chương này.
1 bài học trong chương sẽ tự bỏ nhãn xem thử.

Sau khi ẩn: 2/1 bài học xem thử     Cần bỏ thêm 1
[ ] “Nghe đoạn hội thoại” — Chương 2 · Đã xuất bản
[ ] “Ôn tập nhanh”       — Chương 3 · Bản nháp
(i) Bỏ xem thử không đổi nội dung hoặc trạng thái xuất bản.

[Hủy]                       [Ẩn chương và bỏ xem thử] (disabled until resolved)
```

On stale count, newly pending child, revoked role, moved/deleted topic, or concurrent mutation, keep the dialog open, preserve still-valid selections, fetch a new projection, announce the current reason (`TOPIC_PENDING_FROZEN` takes precedence over quota), and require a new confirm only if the operation remains valid. During submission disable repeated clicks, show progress, and restore controls after failure. Topic-delete quota conflicts use the same inline selection grammar while preserving D1's own published-delete and pending-cancellation confirmations; deletion always clears that topic's Preview marker atomically, and a later restore leaves it unmarked until an authorized author explicitly marks it again. A D1-only deleter without marker authority sees a handoff message to an owner/co-owner/editor if outside markers must be removed. Do not silently unmark unrelated topics. Platform-admin takedown uses its audited RPC, not this authoring dialog: it cancels pending submissions, returns affected pending topics to draft, clears target-owned Preview markers, then hides the chapter atomically even if quota becomes over cap.

## 4. Public syllabus and Preview practice

Replace the temporary badge with a real `Xem thử` badge and `Xem thử bài học` link **only** on eligible published marked rows while allocation is valid. Published unmarked rows retain the locked label; draft/pending/removed rows are absent. When `M > cap`, suppress **all** Preview links and show one generic course-detail notice: `Tính năng xem trước nội dung của khóa học này đang tạm thời không khả dụng.` Do not reveal the count, audit target, reason, or moderator. The course enrollment card retains `Tiếp tục học` for enrolled actors and enrollment/payment CTA for others where the course remains eligible. A user already enrolled may still click a syllabus Preview link and stay on Preview; do not redirect to `/learn` or switch to persistent mode.

Proposed route: `/courses/[course-slug]/preview/[topic-slug]`. It shows course/topic breadcrumb, `Đang xem thử`, and `Tiến độ trong lượt xem thử này không được lưu` near the practice controls. Cards use the presentational `FlashcardStage` with a local queue; Again/Hard requeue in this session and Good/Easy remove locally. Exercises show option selection, request immediate stateless correctness, and reveal explanation after evaluation. Do not initially serialize the answer key. A local step indicator describes the current Preview session only; avoid persisted completion vocabulary. End state offers `Về khóa học` and, only if already enrolled, the separate `Tiếp tục học` route. Neighboring locked topics are never navigable from this route.

Fresh navigation, answer evaluation, and private media fetch recheck eligibility **including current `M <= cap`**. On marker revocation, unpublished course/topic, removed parent, or over-cap suspension, show the same unavailable state without cached content or answer detail and offer `Về khóa học`. If an eligibility-changing event occurs while a user already has content in memory, stop new guarded requests and clear visible protected content on the next server response; already downloaded bytes cannot be recalled. Ordinary error/retry messages must not imply saved progress. The guest needs no signup to use Preview. Once allocation reaches `M <= cap` through valid batch unmark or sufficient denominator growth, otherwise eligible Preview links and requests work again without a separate reactivation step.

## 5. States, accessibility, and verification design

Role/state matrix for UI review:

| State | Teacher | Public/Preview |
| --- | --- | --- |
| Eligible, capacity available | Marker control enabled; used/cap/remaining visible | Published marked topic linked |
| At cap | Unmarked controls disabled with reason; existing marks removable | Existing eligible links remain |
| Draft/pending marked | Counts against cap; `Chưa công khai` explanation | Absent from syllabus/Preview |
| Editor on other's chapter | No chapter mutation/reorder; marker control remains if topic active | No change |
| Previewer | Read-only Structure; no marker or chapter mutation | No change |
| Ordinary hide with active pending child | D1 frozen explanation; no quota resolution or review cancellation | Existing public eligibility remains until another valid transition |
| Hide chapter, quota valid | Destructive consequence plus automatic internal-marker notice | Future chapter reads close |
| Hide chapter, over cap | Inline outside-marker selection and projected allocation | No partial public change |
| Moderation takedown creates `M > cap` | Owner/co-owner/editor see exact allocation, excess and verified causal audit reason/target; previewer has no details; batch unmark CTA | Generic notice; every Preview link/content/answer/media request denied; course detail/enrollment remains eligible |
| Denominator grows during suspension, still `M > cap` | Updated count/excess; causal warning remains | Preview stays unavailable |
| Allocation recovered to `M <= cap` by unmark or denominator growth | Warning clears after server refresh; no reactivation action | Otherwise eligible Preview resumes automatically |
| Stale/error/pending | Dialog retains selection, refreshes projection, no duplicate submit | Uniform unavailable or retry without protected stale data |

Use semantic buttons, checkbox labels with topic title, visible focus, `aria-live` for allocation/stale messages, and a labelled accessible dialog. Tooltip information must be available by keyboard and touch; essential meaning stays in visible text. Focus starts at dialog title, remains trapped while open, returns to the originating hide button on close, and moves to the first unresolved selection when resolution is required. Long titles wrap; long marked lists scroll inside a viewport-safe dialog while its actions remain reachable. At 320/375px use one column and full-width actions; verify tablet and desktop, no horizontal overflow, minimum practical touch targets, and reduced-motion behavior. Do not change shared dialog defaults for this feature.

Implementation QA should use the plan's deterministic role/data fixtures, compare before/after persistent learning rows for enrolled Preview, verify keyboard selection and cancellation, inspect actual mobile layouts and dialog scrolling, and test revocation while the page is open. Static design review does not count as browser QA.

## 6. Self-review gate

The design uses the current Structure/Sheet/Settings/syllabus/workspace visual system and the plan's owner/co-owner/editor/previewer matrix. It distinguishes marker from publication, chapter creator from course-wide marker authority, and Preview from enrolled learning. Ordinary chapter hide honors D1's active-pending freeze before either quota-dialog variant; platform moderation uses the separate audited cancel→draft→takedown path without a moderator marker picker. Internal marker cleanup and explicitly selected external unmarks are distinct; cancellation and stale projection preserve atomicity. The teacher warning is a compact recovery control tied to an exact audit event, while public copy remains generic and enrollment continues. Public content, answer and media fail closed until allocation becomes valid by batch unmark or permitted denominator growth; the causal warning then disappears. The proposed layout and copy cover desktop, mobile, keyboard and error states without a new global component system.

**DESIGN=PASS (self-review, 2026-09-24).** The current plan and repository support each described state, including warning clearance and automatic public recovery after denominator growth; no product UI or browser validation has yet occurred. Implementation still requires separate authority and the planned verification checkpoints.
