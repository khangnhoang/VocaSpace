# AD2 detail plan — course listing approval

Revision: r3, 2026-10-14. Owner approval: 2026-10-14. Master plan: [plan.md](../../plan.md) (unit AD2, Outcome 2, decisions 3–6, invariants 1–3 and 6).

## 1. Binding Spec

### 1.1 Outcome and acceptance

Outcome: after this unit merges and its migration is on hosted, a course reaches the public catalog only when an active admin approves it. The course owner or co-owner submits a `draft` course that has at least one active published topic (`draft` → `pending`) and may withdraw it (`pending` → `draft`); an admin approves (`pending` → `published`) or rejects with a reason (`pending` → `draft`). No signed-in user can change course `status`, `submitted_at`, `reviewed_at`, `reviewed_by` or `reject_message` with a table update (ADMIN-002). Courses that are `published` today stay published.

| ID | Observable result |
| --- | --- |
| AC1 | Submit. `submit_course_review(p_course_id uuid)` succeeds only for a caller whose profile is active (`profiles.removed_at is null`) and who is the course's `owner` or `co_owner` in `course_collaborators`, both read after the course lock is taken (AC5), on a course that exists, has `removed_at is null`, is `draft`, and has at least one topic with `status = 'published'`, `removed_at is null`, in a chapter with `removed_at is null`. It sets `status = 'pending'`, `submitted_at = now()`, and clears `reject_message`, `reviewed_at`, `reviewed_by`. Refusals, each with its own error code: no session (`AUTH_REQUIRED`); `editor`, `previewer`, a non-member, a removed profile, or a global admin or teacher who is not owner or co-owner (`COURSE_SUBMIT_FORBIDDEN`); course missing or removed (`COURSE_NOT_FOUND`); status not `draft` (`COURSE_REVIEW_STATE_INVALID`); no active published topic (`COURSE_SUBMIT_NOT_READY`). A refused call changes nothing. |
| AC2 | Withdraw. `withdraw_course_review(p_course_id uuid)` succeeds only for a caller who passes the AC1 caller check (active profile, `owner` or `co_owner`, read under the lock) on a `pending`, not removed course; it sets `status = 'draft'` and `submitted_at = null` and leaves the review columns as they are (they were cleared at submit). Refusals use the AC1 codes (`AUTH_REQUIRED`, `COURSE_SUBMIT_FORBIDDEN`, `COURSE_NOT_FOUND`, `COURSE_REVIEW_STATE_INVALID`). |
| AC3 | Approve. `approve_course_review(p_course_id uuid)` succeeds only for an active admin (`profiles.role = 'admin'` and `removed_at is null` for `auth.uid()`; anyone else gets `ADMIN_COURSE_REVIEW_FORBIDDEN`), on a not removed course that is `pending` with `submitted_at is not null` (else `COURSE_REVIEW_STATE_INVALID`), and that still has an active published topic at approval time (else `COURSE_SUBMIT_NOT_READY`, the course stays `pending`). It sets `status = 'published'`, `reviewed_at = now()`, `reviewed_by = auth.uid()`, `reject_message = null`. An admin who is also the course's owner or co-owner may approve it (Owner, 2026-10-14). After approval the course is listed by `get_public_course_catalog` (existing filter `status = 'published' and removed_at is null`). |
| AC4 | Reject. `reject_course_review(p_course_id uuid, p_reason text)` has the AC3 admin and state checks; the reason, trimmed, must be 10–1000 characters (else `COURSE_REJECT_REASON_INVALID`), matching `rejectCourseSchema` (`lib/schemas/admin-course.ts`). It sets `status = 'draft'`, `submitted_at = null`, `reject_message` = the trimmed reason, `reviewed_at = now()`, `reviewed_by = auth.uid()`. It does not re-check topic readiness. |
| AC5 | Locking and safety of the four RPCs: each is `security definer` with a fixed `search_path` set the way the newest course RPCs set it, takes `pg_advisory_xact_lock(hashtext(p_course_id::text))` before any row lock, then reads the course row `for update`, then checks the caller (admin profile, or profile plus membership) and the state; all checks run after the lock, so a call that waited sees the result of whatever held the lock (for example approve after withdraw gets `COURSE_REVIEW_STATE_INVALID`; submit after the caller was demoted to `editor` or removed from the course by `update_course_collaborator_role` or a removal RPC, which take the same lock, gets `COURSE_SUBMIT_FORBIDDEN`). Execute is revoked from `public`, `anon` and `service_role` (default function privileges grant `service_role`, `20260609114505_remote_schema.sql:2127`) and granted to `authenticated` only; checked with `has_function_privilege`. Each returns the `course_id` (and new `status`) on success. |
| AC6 | Column lock-down (ADMIN-002 exit). `anon` and `authenticated` lose table-level `UPDATE` on `public.courses`; `authenticated` gets column `UPDATE` on exactly `title`, `slug`, `description`, `price`, `thumbnail_url`, `removed_at` (the columns `updateCourse` and `deleteCourse` write, `app/actions/course.ts:275-276`, `:382-417`). The RLS policy `Courses - Staff Update Secured` is unchanged. Observable: a signed-in owner, co-owner, editor, global admin and teacher each get SQLSTATE `42501` when updating `status`, `submitted_at`, `reviewed_at`, `reviewed_by` or `reject_message` (one update per column, row unchanged, read back as service role); an editor still updates `description` (existing `course-creation-rls.test.ts:371-377`); `updateCourse` and `deleteCourse` keep working; service-role writes are unaffected. |
| AC7 | Legacy data. The migration sets every course with `status = 'pending'` and `submitted_at is null` to `draft` (Owner, 2026-10-14). On hosted this updates no row (§2 inventory). `supabase/seed.sql` changes the pending seed row `b2-qa-hidden-pending` to `draft` (seed runs after migrations, so it would otherwise recreate the legacy state); tests that relied on a seeded pending course create their own pending fixture as service role. Published courses are not touched. |
| AC8 | Teacher UI. On the course overview, on both its branches (the full dashboard's "Việc tiếp theo" aside in `CourseOverview.tsx`, and `EmptyCourseDashboard`, which `CourseOverview.tsx:70-72` renders when the course has no active chapter — reachable while `pending` because edits stay allowed), the course's owner or co-owner sees: "Gửi duyệt" on a `draft` course (disabled with the hint "Cần ít nhất 1 bài học đã xuất bản để gửi duyệt." when the readiness data shows no published topic); "Rút yêu cầu duyệt" on a `pending` course, behind a confirm dialog (`components/ui/confirm-dialog.tsx`); nothing on a `published` course. Editors see the status badge only. Previewers keep today's page: `getCourseDashboardReadiness` returns `PREVIEWER_STRUCTURE_ONLY` for them (`app/actions/course-readiness.ts:173-178`), unchanged. On success a sonner toast confirms and the page refreshes to the new status; on failure the mapped Vietnamese message is shown as an error toast and the status is unchanged. A `draft` course whose last review was a rejection (`reviewed_at` and `reject_message` set) shows the reason on both branches, as the course list banner already does (`CourseList.tsx:116-131`). The published-topic signal and the review fields are computed on the server and carried in `CourseDashboardReadiness` (see §3). |
| AC9 | Admin actions, no screen. `approveCourseReview` and `rejectCourseReview` Server Actions validate input with `acceptCourseSchema` and `rejectCourseSchema`, require a signed-in user, call the RPC with the user's client, map error codes to Vietnamese messages, revalidate the teacher course paths and `/courses`, and return `{ success: true, data }` or `{ error }`. The RPC's active-admin check is the server check of master invariant 1 (the action holds no privilege of its own; it uses the caller's session). No admin page or link is added (AD3). |
| AC10 | Docs: progress State describes AD2 while it runs; at the final CP ADMIN-002 moves to `Resolved` with the evidence, a milestone records the unit; `npm run docs:check` reports no new broken link. |

### 1.2 Scope and non-goals

- In scope: AC1–AC10; one migration; seed change; the guard change of two integration suites (§3); teacher Server Actions `submitCourseReview` and `withdrawCourseReview` (input `submitCourseReviewSchema`); admin Server Actions of AC9; the readiness/overview data needed for AC8 (course `reject_message`, `reviewed_at`); `types/database.ts` additions if needed; tests in §4.
- Non-goals:
  - the admin course screen, demote and takedown UI (AD3);
  - removed-admin checks in existing SQL such as `moderate_platform_content` and `is_admin()` (AD7, ADMIN-004);
  - notifications or email on submit, approve or reject;
  - re-review after edits to a published course (decision 6: edits take effect at once);
  - freezing edits while `pending` (Owner, 2026-10-14: edits stay allowed while pending; the admin reviews what is there at approval time);
  - any change to topic review, topic publication, course membership, the catalog read model, or `moderate_platform_content`;
  - revoking `INSERT`/`DELETE` table grants (no policy allows them; covered by existing tests);
  - an audit table for approve or reject (the course row keeps `reviewed_by`, `reviewed_at`, `reject_message`).

### 1.3 Execution guardrails

| Guardrail | Failure if omitted |
| --- | --- |
| G1. The lock-down revokes table-level `UPDATE` and then grants column `UPDATE`; it never relies on a column-level revoke alone (a table-level grant covers every column). | `authenticated` can still set `status` after the migration (ADMIN-002 stays open). |
| G2. Before the migration, the implementor lists every client-session writer of `public.courses` (`rg "from\(\"courses\"\)"` over `app/`, `lib/`, `components/`, `utils/`) and confirms it writes only the AC6 columns. A client writer of any other column is a stop condition, not a reason to widen the grant. | The lock-down breaks an existing app write in production. |
| G3. Each RPC takes the course advisory lock before any row lock (master invariant 3, `student-user-flow-route` Decision 31); none locks a structure row before it. | New deadlocks with structure edits. |
| G4. Admin RPCs check `profiles.role = 'admin' and removed_at is null` for `auth.uid()` inside the function; submit and withdraw check `profiles.removed_at is null` and `course_collaborators` role in (`owner`, `co_owner`), not `has_course_authoring_access` (that includes `editor`); every caller check runs after the course lock. | A removed admin approves, an editor submits (decision 4), or a check made before the lock keeps a role the caller lost while waiting. |
| G5. Local integration and browser runs use the isolated runtime (API 45441, DB 45442) with migrations applied there; port 3100 and `.next-e2e` for a browser run. Root 45321/45322 and hosted are never reset or written by the implementor; no `db push`. No worktree `node_modules` junction removal. | A run writes the Owner's data or hosted, or wipes `node_modules`. |
| G6. Each CP runs only the tests it names; the final CP runs the AD2 integration file and the changed existing suites on the isolated runtime, and the whole integration directory runs in CI. | Root data gets written, or the change ships without the full integration run. |

## 5. Risks, rollout and rollback

| Risk | Mitigation |
| --- | --- |
| The lock-down breaks a client write not found by the inventory | G2 inventory; AC6 column list from the only two writers; existing editor test; hosted has no app path writing other columns |
| A submitted course waits in `pending` with no admin screen | Ship AD3 right after AD2 (master plan risk); teachers can withdraw |
| Approve publishes a course whose topics were unpublished after submit | AC3 re-check at approval |
| Concurrent submit/withdraw/approve leave inconsistent review fields | AC5 lock order and state checks inside the lock; concurrency test in CP2 |
| The seed change breaks a test or smoke spec that expects a seeded pending course | CP2 runs the suites that read it; any other reader found by `rg b2-qa-hidden-pending` gets its own fixture |

- Rollout runbook (master plan §5): CI green → with a separate Owner grant, `supabase db push` to hosted → read-only verify: migration listed; the four RPCs exist with execute for `authenticated` only; `authenticated` has no table-level `UPDATE` on `courses` and column `UPDATE` only on the AC6 columns; no `pending` row with `submitted_at` null → merge and the production deploy. The old app never writes the locked columns, so pushing before the deploy is safe. Root 45321 gets the migration only when the Owner asks (`supabase migration up --local`, no reset).
- Stop when: a client writer of a locked column exists (G2); the advisory lock cannot be taken first; hosted shows a `pending` course at rollout time (needs an Owner decision before the push); any test outside the named suites fails because of the change. Report to the Owner.
- Rollback, with a separate Owner grant for the hosted step: (1) revert the app and deploy, which removes the controls (the RPCs still exist, so nothing calls a missing function); (2) a forward migration, in one transaction, revokes execute on `submit_course_review` from `authenticated` (no new submission), restores table-level `UPDATE` on `public.courses` to `authenticated`, and moves every `pending` course to `draft` with `submitted_at` null; withdraw, approve and reject stay; (3) after the migration commits, wait until no backend is still running `submit_course_review` (`pg_stat_activity`), since a submit that started before the revoke can commit after the update; then run the same `pending` → `draft` update once more and confirm no `pending` course is left. Until that check passes, the rollback is not complete. Courses already approved stay `published`. Restoring the grant reopens ADMIN-002, recorded in problems.md.
