# AD3 detail plan — admin course screen

Revision: r4, 2026-10-14. Owner approval: 2026-10-14. Master plan: [plan.md](../../plan.md) (unit AD3, Outcome 3, decisions 6–7, invariants 1–3).

## 1. Binding Spec

### 1.1 Outcome and acceptance

Outcome: an active admin opens `/admin/courses` from the admin sidebar and sees the real courses with their owner, status and review fields. From that screen the admin approves a submitted course, rejects it with a reason, and demotes or takes down a published course with a reason. Each change goes through an existing security-definer RPC; the screen reads with the admin's own session (no service-role read, no migration).

| ID | Observable result |
| --- | --- |
| AC1 | Route and gate. `app/admin/courses/page.tsx` calls `requireAdminPage()` before any read. A guest is redirected to `/login?reason=signin_required` (existing proxy); a student, a teacher, and an admin whose profile has `removed_at` set get the not-found page with no admin shell; an active admin gets 200 with the admin shell. The admin sidebar lists three links in this order: "Dashboard" (`/admin`), "Quản lý User" (`/admin/user-management`), "Quản lý khóa học" (`/admin/courses`); "Quản lý khóa học" is active on `/admin/courses` and its sub-paths only. |
| AC2 | List data. The page reads `courses` with the admin's server client (`@/utils/supabase/server`), relying on the admin branch of `can_view_course_basic` (Owner, 2026-10-14). Each row shows: title and slug; owner `full_name` (the `course_collaborators` row with `role = 'owner'`, joined to `profiles`; "—" when the owner's profile is not readable, for example removed); status badge (`Bản nháp`, `Chờ duyệt`, `Đã xuất bản`, `Đã gỡ`); price (`Miễn phí` for 0, VND otherwise); `submitted_at`; `reviewed_at`; the rejection reason of a `draft` course whose `reviewed_at` and `reject_message` are set; and, on the removed tab, `removed_at`. No value on the screen is mock or placeholder data; a value the database does not hold is shown as "—". |
| AC3 | Filters, search, paging, all from the URL and parsed on the server with `adminCourseFilterSchema` (`lib/schemas/admin-course.ts`): `status` in `pending` (default), `published`, `draft`, `all`, `removed`; `q` (trimmed, at most 100 characters) matches title or slug case-insensitively; `page` (from 1) with a fixed page size of 20. Tabs `pending`, `published`, `draft`, `all` show only courses with `removed_at is null` (`all` = every status); `removed` shows only courses with `removed_at` set (Owner, 2026-10-14). Order: `pending` by `submitted_at` ascending (oldest first); `removed` by `removed_at` descending; the others by `updated_at` descending; `id` breaks ties. Each tab shows its count for the current `q`. An invalid parameter falls back to its default instead of an error. A page beyond the last shows the empty state with a link back to page 1. `q` is never interpolated raw into a PostgREST filter string (G3); `%`, `_`, `,`, `(`, `)`, `"` and `\` in `q` match literally. |
| AC4 | Course summary. Selecting a row opens a read-only summary panel (sheet or dialog, no route change) with: cover image (or a neutral placeholder when `thumbnail_url` is null), title, slug, description, price, owner, status, `submitted_at`, `reviewed_at`, `reject_message` when shown by AC2, and the chapter and topic outline: chapter titles in `order_index` order, each with its topic titles in order and a status label per topic (`Đã xuất bản`, `Chờ duyệt`, `Bản nháp`), plus the count of active published topics. Only active chapters and topics (`removed_at is null`) are listed; reads use the admin's session (chapters `Select chapters credential bound`, topics `Select topics credential bound` admit an active admin). The panel does not show topic content (cards, exercises, media) (Owner, 2026-10-14; content preview is a future feature). The outline is read in full regardless of the API row limit (`max_rows = 1000`, `supabase/config.toml:18`), using `readAllSupabaseRows` (`lib/supabase-pagination.ts:13`) or an equivalent paged read. The summary is loaded by a Server Action `getAdminCourseSummary({ courseId })` when the panel opens: it parses `courseId` (uuid), requires an active admin in that request before any query (G1), and returns `{ success: true, data }` or `{ error }`; invalid input, no session, a non-admin and a removed admin get `{ error }` and run no summary query. A load failure shows an error with a retry, not an empty outline. The panel's actions are the row's actions (AC5–AC7). |
| AC5 | Approve. A `pending` row has "Duyệt" opening a confirm dialog that names the course, says the course becomes public in the catalog, and calls the existing `approveCourseReview` action. Success: sonner toast, the dialog closes, the list refreshes and the course leaves the `pending` tab. Failure: the mapped Vietnamese message stays in the dialog (or a toast) and the list is unchanged. `COURSE_SUBMIT_NOT_READY` and `COURSE_REVIEW_STATE_INVALID` (for example the teacher withdrew meanwhile) keep their AD2 messages and the list refreshes. |
| AC6 | Reject. A `pending` row has "Từ chối" opening a dialog with a required reason (10–1000 characters, counted like `rejectCourseSchema`), a live character count, a field error under the textarea, and the consequence (the course returns to draft and the teacher sees the reason). It calls `rejectCourseReview`. On a recoverable error the reason stays in the field. Success: toast, the course leaves `pending`; the reason then shows on the `draft` tab row. |
| AC7 | Demote and takedown. A `published` row with `removed_at is null` has "Hạ về bản nháp" and "Gỡ khóa học", each opening its own dialog with a required reason and the consequence: demote — the course leaves the public catalog and returns to draft, the teacher can submit again; takedown — the course is removed from the catalog and from teaching, is listed on the `Đã gỡ` tab, preview markers are cleared, and the screen offers no restore. Both call a new Server Action `moderateCourse` (§1.3 G2) with `{ courseId, action: 'demote' \| 'takedown', reason }`, which calls `moderate_platform_content('course', courseId, action, reason)`. Reason: trimmed, 10–2000 characters (`platformModerationSchema` limits; the RPC requires non-empty and at most 2000). On a recoverable error the reason stays. Success: toast, list refresh; demote moves the course to `draft`, takedown to `removed`. `draft` and `removed` rows have no action (decision 7 covers published courses; `pending` is handled by approve or reject). |
| AC8 | Server checks. `moderateCourse` validates input with a Zod schema in `lib/schemas/admin-course.ts`, then requires an active admin (`profiles.role = 'admin'` and `removed_at is null` for the session user) before the RPC call (Owner, 2026-10-14: the action closes the RPC's missing `removed_at` check for this screen; the RPC fix stays in AD7/ADMIN-004). Refusals return `{ error }` without calling the RPC: invalid input; no session; not admin or removed admin. RPC error codes map to Vietnamese messages: `AUTH_REQUIRED`, `ADMIN_MODERATION_FORBIDDEN`, `MODERATION_REASON_REQUIRED`, `MODERATION_REASON_TOO_LONG`, `MODERATION_TARGET_NOT_FOUND`, `MODERATION_TARGET_STATE_INVALID` (course no longer published), `MODERATION_TARGET_ALREADY_REMOVED`; anything else gets the generic message. Success returns `{ success: true, data }` and revalidates `/admin/courses`, the course's teacher overview and structure paths, the teacher course list and the public catalog (the same set as `admin-course-review.ts` plus `/admin/courses`); `approveCourseReview` and `rejectCourseReview` also revalidate `/admin/courses`. The list read path in AC2–AC4 runs only after `requireAdminPage()`. |
| AC9 | States and accessibility (frontend-design, Admin / Business Operations, admin is dark-only). Empty state per tab (for example "Không có khóa học nào đang chờ duyệt."), empty search result with a clear-search action, list load error with retry, pending state on each submit button with a busy label and double submit blocked, dialogs that trap focus and return it to the trigger, every control labelled (no icon-only button without an accessible name), status not conveyed by color alone, the table usable at 1280 px and the layout usable at 375 px (rows may collapse to cards). Destructive buttons ("Từ chối", "Gỡ khóa học") are not adjacent to their confirming counterparts without separation. WCAG 2.2 AA contrast on the dark admin surface. |
| AC10 | Docs: progress State describes AD3 while it runs; `/privacy` gains one sentence saying that VocaSpace admins see a course's author name and the course's content when reviewing, demoting or taking down a course (Owner, 2026-10-14; the exact wording is approved by the Owner in the PR before merge; `/terms` unchanged); `future-features.md` of the program records the admin in-place lesson preview direction; a milestone records each CP; `npm run docs:check` reports no new broken link. |

### 1.2 Scope and non-goals

- In scope: AC1–AC10; `app/admin/courses/page.tsx` and its `_components` (the existing mock components are reworked or replaced; nothing on the final screen is mock); a server-only read module for the list and the summary; `moderateCourse` and its schema; the revalidation additions to `admin-course-review.ts`; the sidebar link; the `/privacy` sentence of AC10; the updates of the AD1 tests and scripts that assert `/admin/courses` is removed (§2); tests in §4.
- Non-goals:
  - any migration, RPC, RLS or grant change (Owner, 2026-10-14);
  - the `removed_at` check inside `moderate_platform_content`, `is_admin()`, `can_view_course_basic` (AD7, ADMIN-004);
  - restoring a removed course; chapter- or topic-level moderation from this screen; `invalidate_review`;
  - topic content preview (cards, exercises, media) in the admin UI (future feature, recorded in AC10);
  - owner email (needs the service-role email reader; full name is enough to identify the owner here);
  - enrollment counts or revenue on this screen;
  - notifications or email on approve, reject, demote or takedown;
  - changing `approveCourseReview` / `rejectCourseReview` beyond the revalidation path (their active-admin check is in the RPC, AD2 AC9);
  - the dashboard (AD4) and other admin units.

### 1.3 Execution guardrails

| Guardrail | Failure if omitted |
| --- | --- |
| G1. Reads in the page's server render (list, counts) run after `requireAdminPage()` in that render; the summary read runs only inside `getAdminCourseSummary` after its own active-admin check in the same request (a Server Action is a separate entry point and cannot rely on the page gate). All reads use the caller's session client; no service-role client is imported by the page, its loaders, `getAdminCourseSummary` or `moderateCourse`. | A non-admin or removed admin reads draft and removed courses, or a privileged client hides a missing gate. |
| G2. `moderateCourse` lives in `app/actions/admin-course-review.ts` (or a sibling `admin-course-moderation.ts`), accepts only `courseId`, `action` (`demote`, `takedown`) and `reason`, fixes `p_target_type` to `'course'` on the server, and checks the active admin before calling the RPC. It does not reuse `moderatePlatformContent` in `topic-review.ts` (that action has no active-admin check and accepts any target type). | The client picks another target type or action, or a removed admin moderates through this screen. |
| G3. The search term is applied with typed query-builder filters whose values are escaped for `ilike` (`\`, `%`, `_`), and, if `.or()` is used, each value is double-quoted with `"` and `\` escaped per PostgREST rules. A test sends a `q` with `%`, `_`, `,`, `(`, `)` and `"` and asserts a literal match and no error. | A crafted `q` changes the filter (for example matches everything or breaks the query), turning search into a read-scope bug. |
| G4. Counts and pages come from the database (`count: 'exact'` and `range`), not from filtering a full list in memory. | At the root runtime's 540 courses the page loads every row and the counts drift from the shown page. |
| G5. The UI never decides permission: buttons follow status for usability, but every action result is the server's; a refused or stale action shows the server message and refreshes the list. | A stale row lets the admin believe an action succeeded. |
| G6. Local integration and browser runs use the isolated runtime (API 45441, DB 45442), port 3100 and `.next-e2e`; root 45321/45322 and hosted are never reset or written by the implementor. No worktree `node_modules` junction removal. | A run writes the Owner's data or hosted, or wipes `node_modules`. |
| G7. The AD1 gate coverage keeps its meaning: guest redirect for `/admin/courses`; student and teacher not-found for `/admin/courses`; revoked admin not-found on client navigation to "Quản lý khóa học"; `/admin/stats` and `/admin/settings` stay not-found. Only the expectations that `/admin/courses` is a removed route change. | AD3 silently weakens the AD1 gate evidence. |

## 3. Bounded implementation hypotheses

- A server-only module (for example `lib/admin/course-list.ts`, `import "server-only"`) holds the list and outline queries using `createClient` from `@/utils/supabase/server`; DTO types next to the schema or the module. The page calls the list query after `requireAdminPage()`; the Server Action `getAdminCourseSummary` (next to `moderateCourse`) calls the outline query after its active-admin check.
- The page is a server component reading `searchParams`; the client part (tabs, search input with submit or debounce that updates the URL, table, panel, dialogs) is one client component tree under `_components/`, reusing `components/ui` primitives (`Tabs`, `Input`, `Badge`, `Button`, `Sheet` or `Dialog`, `AlertDialog`/`confirm-dialog.tsx`, `Textarea`) and sonner.
- One shared active-admin helper for Server Actions (for example a non-throwing `getActiveAdminUserId()` beside `requireAdminPage` in `lib/auth/admin-access.ts`), used by `moderateCourse` and `getAdminCourseSummary`.
- `moderateCourseSchema` in `lib/schemas/admin-course.ts`: `courseId` uuid, `action` enum `demote|takedown`, `reason` trimmed 10–2000; `getAdminCourseSummary` reuses `acceptCourseSchema`'s `courseId` shape or a small `adminCourseIdSchema`.

## 5. Risks, rollout and rollback

| Risk | Mitigation |
| --- | --- |
| A removed admin still reads courses through `can_view_course_basic` with a direct API call | Accepted until AD7 (ADMIN-004); the page gate blocks the screen and `moderateCourse` blocks moderation; approve/reject RPCs already check `removed_at` |
| Takedown cannot be undone from the UI | Dialog states it; reason and previous state are audited in `platform_moderation_audits`; restore is a non-goal |
| Admin approves with too little context | Summary panel with outline and published-topic count (AC4); lesson try-out recorded as a future feature |
| Search input breaks the PostgREST filter | G3 escaping and its test |
| Gate tests weakened while updating AD1 expectations | G7 lists what must stay; CP4 runs the gate spec and the production status check |
