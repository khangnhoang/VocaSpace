## 1. Binding Spec

### 1.1 Outcome and acceptance

Outcome: the payment screens a student sees have English text behind the U1 flag:

- the enrollment card's checkout toasts, the payment modal with its discount stage, free-enrollment stage and QR stage on `/courses/[course-slug]`, including the resumed checkout opened by `?thanh-toan=tiep-tuc`;
- the pending-payment card on `/learn` (`PendingPayments.tsx`);
- the payment history section of `/profile` (`payment-history.tsx`).

With the flag off, they render exactly the Vietnamese they render today, except the one checkout error that decision 4 replaces. With the flag on and English active, they show no Vietnamese outside the categories AC2 allows, and their errors, toasts, accessible names, dates and amounts follow the active language on the client and the server. Prices stay in VND.

### 1.2 Scope and non-goals

In scope:

- **Components.** `PublicCourseEnrollmentCard.tsx` (checkout toasts and `ResumePaymentEntry`), `PublicCoursePaymentModal.tsx`, `PublicCoursePaymentStageDiscount.tsx`, `PublicCoursePaymentStageQr.tsx`, `app/(client)/learn/_components/PendingPayments.tsx`, `app/(client)/profile/_components/payment-history.tsx`. In `PublicCourseDetailRoute.tsx` and `PublicCourseDetailView.tsx`, only receiving and passing on the QR placeholder key of the resumed checkout (H5); `resumeCheckout`, the condition that calls the action and their existing assertions stay unchanged.
- **Actions.** `app/actions/payment.ts`, `payment-history.ts`, `discount.ts`, the messages of `lib/discounts/discount-pricing.ts`, and new `*-localized.ts` wrappers for the client-called actions (H3).
- **Schemas and helpers.** The messages of `lib/schemas/payment.ts` and `lib/schemas/discount.ts` (as keys, H4), and `lib/payment-history-format.ts` (status labels, locale-aware date and amount forms beside the existing ones).
- **i18n wiring.** A `payments` namespace for both locales in `MESSAGES` and its delivery to the course, profile and learn subtrees (H1, H2).
- **Tests.** New English, locale-switch and action tests, the setup-only edits G6 allows, and the removal of the U5 exclusions from `learn-dashboard-english.test.tsx` and `profile-english.test.tsx` when their surfaces become English.

Non-goals:

- **PayOS and webhooks.** `app/api/webhook/payos/route.ts` and `app/api/cron/expire-payments/route.ts` answer PayOS or the scheduler, not a student, and stay unchanged. The PayOS order description and the transfer text `VOCASPACE <order>` stay as they are (master invariant).
- **Admin payments (U10).** Admin payment and discount screens, `lib/admin`, and `LEARNER_HAS_ACTIVE_PAYMENT` in `app/actions/user.ts`.
- **Behavior.** No change to pricing, discount reservation, payment status rules, expiry, Realtime subscription, redirects, query parameters (`thanh-toan=tiep-tuc`) or stored data. No `supabase/seed.sql` change (decision 3).
- **Other units.** The U2 parts of the course page and profile, the U3 parts of `/learn`, emails (U6).

### 1.3 Execution guardrails

| Guardrail | Failure if omitted |
| --- | --- |
| G1. Apart from the decision 4 message, Vietnamese strings move into the catalog verbatim, checked by the unchanged Vietnamese assertions or an exact comparison, never by retyping. This includes today's mixed amount forms (`đ`, ` ₫`, ` VNĐ`) and the `toLocaleString()` calls without a locale, whose Vietnamese output stays byte-identical. | A silent Vietnamese wording or amount change. |
| G2. Every action keeps its response shape, unions, error codes and side-effect order; a message is a catalog key translated where the action returns it and recorded with `recordedTranslations`, never looked up from translated text. The PayOS call arguments never depend on the locale. | Clients branch differently by language, a raw key reaches the user, or a PayOS order changes. |
| G3. Code that reacts to an error branches on a code, status or `type`, never on message text. U5 adds no text-matching branch. | English messages take the wrong branch. |
| G4. Each subtree that renders a U5 surface receives `payments` through `ClientNamespaces` together with every namespace it already gets (a nested provider replaces its parent's messages). | A raw key reaches the user on one route. |
| G5. The locale selects only text and formatting: prices, discount amounts, the currency, status values and time zone stay the same. | A tampered or English locale changes what a student pays. |
| G6. Existing tests change only in these ways: render setup moves to the shared provider; an import path changes when a string moves; an action mock returns its message through `recordedTranslations` with the same Vietnamese text when the client under test needs the key; a namespace-delivery expectation (for example in `courses-client-boundary.test.tsx`) follows H2; the U5 exclusion comments and mocks in `learn-dashboard-english.test.tsx` and `profile-english.test.tsx` are replaced by English assertions for those surfaces; an assertion of the old raw-error text changes to the decision 4 text. Any other changed assertion stops the work and goes to the Owner with the evidence. | Test edits hide a wording or behavior regression. |
| G7. Code outside section 1.2 stays untouched apart from G6 setup. | U5 grows into U2, U3 or U10 territory. |
| G8. With the flag off, the U1 resolver still returns `vi` without reading request data, and U5 adds no other locale read. | Routes change rendering mode, or English leaks before step A. |

## 3. Bounded implementation hypotheses

- **H1, namespace.** A new `payments` namespace holds the checkout, discount, QR, pending-card, history and action texts, and the discount schema keys sit in `validation`. Names may change while G4, AC8 and the parity test hold.
- **H2, delivery.** `payments` is added to the three layouts above. Server components may pass translated strings as props where simpler. CP1 checks the delivery on a real build.
- **H3, client-called messages.** `createCheckoutSession`, `cancelCheckoutSession`, `checkPaymentStatus` and `validateDiscountPreview` get `*-localized.ts` wrappers on the U2 single-key pattern (`withRequestLocale`), and their clients hold each message as a key with parameters and translate it at render or when the toast fires. `getPaymentHistory` translates with `getTranslations` and needs no wrapper, because its client drops failures. If `checkPaymentStatus` messages never reach the UI, it gets no wrapper either; CP1 records which.
- **H4, schema messages.** `checkoutInputSchema` and `discountCouponSchema` emit message keys on the U1 `registerSchema` pattern, translated by the action or the form; accept and reject results stay the same in both locales.
- **H5, QR placeholder.** `router.refresh()` cannot fix this text: the enrollment card copies `resume.data` into state once (around line 77) and `ResumePaymentEntry` removes the resume parameter, and `withRequestLocale` returns no key for a result without `error` or `message` (`request-locale-result.ts` line 29). Two different sentences exist today: the `pending` branch (`buildPendingCheckoutResponse`, line 89) and the new-order branch when PayOS gives no account number (line 373), and `createCheckoutSession` can return either. So each branch records its own catalog key with `recordedTranslations` where it chooses the sentence, and the action result itself stays unchanged. The key travels outside the result: the client wrapper of `createCheckoutSession` returns it next to `result` in its envelope (for example `accountNumberRef`), and the server page gets it from a server-only localized variant of `resumePendingCheckout` and passes it to the card as a separate prop. The QR stage renders the key in the displayed language when it is present and renders `accountNumber` as returned when it is absent (a real PayOS value). The client never detects the placeholder by matching text. Tests: VI → EN → VI while the QR stage is open, for a resumed `pending` checkout and for a new order without an account number; a late response after a cookie change; a real account number shown unchanged; the existing `toEqual` assertions on the action results stay as they are.
- **H6, evidence and fixture.** Snapshot and scan scripts are rebuilt in the session scratchpad on the U3 approach, capture title and description too, and install the same fixed browser clock (Playwright `clock`) before opening the QR stage on both builds. For the QR stage, a scratchpad script on the local stack backs up the row of `b2-qa-payment-2`, sets a fake `qr_code` (and `checkout_url`) in its `gateway_metadata`, and restores the row after the base and candidate captures and QA, and again if a run stops midway; cancelling it during QA is the last step. State records the before and after rows and the confirmed restore. The QR image loads from `api.qrserver.com` as today; a failed image load does not block the text checks. For the applied-code state, CP1 checks read-only whether the local DB already has a discount that applies to a seeded paid course; if none does, that browser state is recorded as blocked and the Owner decides before any row is created (decision 3), while render tests still cover the applied-code UI. No hosted data is touched.
- **H7, formatting.** `lib/payment-history-format.ts` keeps its current exports and output for existing callers and gains locale-aware forms (or the screens call `lib/i18n/format.ts`), with today's Vietnamese output checked for a fixed input set at CP1.

## 5. Risks, rollout and rollback

| Risk | Mitigation |
| --- | --- |
| A Vietnamese string or amount format changes while moving. | G1, the unchanged Vietnamese assertions (AC7) and the AC1 snapshot pairs. |
| Translation changes what PayOS receives or what a student pays. | G2 and G5; the AC3 test compares the PayOS request in both locales; pricing code is not touched beyond its messages. |
| A student sees an old-language checkout error after switching. | AC4 with the U2/U3 mechanism and locale-switch tests. |
| The QA fixture leaves a modified payment row on the local stack. | H6 backup and restore, with both rows recorded in State. |
| A nested provider drops `payments` and a raw key reaches the user. | G4, the CP1 real-build check and the AC2 raw-key scan. |

- Rollout runbook: none. The flag stays off in production, so merging changes nothing visible, with one exception: a student who hits a non-`23505` insert failure in checkout sees the decision 4 message instead of the database text, in Vietnamese.
- Stop when: a Vietnamese assertion must change beyond G6; an AC1 pair differs; the flag-off route table changes; the PayOS request differs between locales; a fix would change pricing, discount or payment status logic; the scope would cross into U2, U3 or U10 files beyond section 1.2.
- Rollback: revert the PR. No data or hosted configuration changes.
