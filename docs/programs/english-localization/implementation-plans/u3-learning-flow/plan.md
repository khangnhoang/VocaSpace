## 1. Binding Spec

### 1.1 Outcome and acceptance

Outcome: the enrolled learner's screens have English text behind the U1 flag:

- the learning dashboard `/learn`, including the review sheet;
- the enrolled course overview `/learn/[course-slug]`;
- the topic workspace `/learn/[course-slug]/[topic-slug]` with its flashcard, memory-check, exercise and completion stages;
- the loading states and metadata of these routes.

With the flag off, they render exactly the Vietnamese they render today. With the flag on and English active, they show no Vietnamese outside the categories AC2 allows. Their errors, toasts, accessible names, metadata, dates, durations and numbers follow the active language on both the client and the server.

| ID | Observable result |
| --- | --- |
| AC1 | **Flag off: text is unchanged.** Every page in the page set renders the same visible text, accessible names, `<title>`, `meta[name="description"]` and `<html lang>` as the base build, whatever `Accept-Language` or the locale cookie says. Rendered at 1440 and 375px, the snapshots of the base build and the final candidate are identical. <br>The page set, signed in as a student: `/learn` with the review sheet closed and open with a due card, `/learn/[course-slug]` for an enrolled course with activity, and a topic page in each of these states: flashcard stage, memory check locked and open, exercise locked and open, an answered question (correct and incorrect), and the completion panel. The data that opens each state is recorded at CP1 (H6). |
| AC2 | **Flag on, English: no Vietnamese leftovers.** The page set is in English, covering visible text, accessible names, title and description. Only these categories may stay Vietnamese: <ul><li>teacher-authored learning content: course, chapter and topic titles, words, meanings, examples, questions, options, passages and authored explanations;</li><li>the user's own data;</li><li>the pending-payment card on `/learn` (`PendingPayments.tsx` and `formatPaymentDate`), which U5 converts (decision 1);</li><li>the accessible name `VI (Tiếng Việt)` of the `vi` button in the U1 language switcher, which names the language on purpose (the same leftover U2 recorded on every page); the rest of the header is still scanned.</li></ul> A diacritics scan of the rendered text and accessible names, followed by a manual check of every hit, shows this. Every remaining Vietnamese string is listed in State with its category. The same scan finds no raw catalog key (`namespace.key`, for every namespace in the catalog). Interface labels without diacritics (the today, weekday and day-month labels of the streak card and the relative-day labels of recent topics) are covered by English render assertions, because the diacritics scan cannot see them. |
| AC3 | **Action messages in both languages.** Each action below returns its translated message on every path that returns a message today, keeps its response shape, error codes and status unions, and keeps returning before a side effect where it does today. The Vietnamese text is exactly today's. Actions: `getLearnDashboard`, `getLearningSummary`, `getCourseLearningSummary`, `getEnrolledCourseOverview`, `getLearningWorkspace`, `submitQuestionAnswer` (including the default explanation of a wrong answer and the `MEMORY_CHECK_REQUIRED` and `CARDS_REQUIRED` messages from `lib/memory-check.ts`), `submitCardReview` and `getDeckReviewCards`. An explanation the author wrote is learning content and stays as written. |
| AC4 | **Messages shown after a language switch or across tabs.** This covers each system text from a client-called action that the UI shows (the `error`, the default wrong-answer explanation and the `progressError` of `submitQuestionAnswer`; the `progressError` of `submitCardReview`; the error of `getDeckReviewCards`) and each client-built message (review save failures, unlock and completion messages). <ul><li>A message that stays on the page (text in the workspace or the review sheet, including `role="status"` and `role="alert"` regions) changes to the new language after the VI/EN switch while it is shown.</li><li>A response that arrives after the switch, or after the cookie changed in another tab, is shown in the displayed language.</li><li>A toast takes the displayed language when it fires. A toast already on screen at the moment of the switch keeps its text until it closes, as U2 toasts do.</li></ul> No message stays in the old language beyond that, and none disappears without a replacement. An authored explanation is shown as written in both cases. This extends the U2 mechanism (`withRequestLocale`, `recordedTranslations`, `HeldMessage`) as H4 describes. |
| AC5 | **Toasts and screen-reader text.** Toasts, status text, `aria-label`, `aria-valuetext`, screen-reader-only text and loading labels in U3 screens follow the active language. The shared components `QuestionNavigator`, `ExerciseContext`, `ChoiceGroup` and `CourseLearningActivity` receive translated labels in U3 screens, as the U2 public preview already does. |
| AC6 | **Formatting.** Study durations, weekday and day-month labels, relative days and counts in U3 screens follow the active language through `lib/i18n/format.ts` or catalog plurals. The `vi` output equals today's output. The day boundary stays the one SQL computes in `Asia/Ho_Chi_Minh`. |
| AC7 | **Existing tests unchanged.** The Vitest unit suite, `npm run test:integration` and the full `npm run test:e2e` pass with their Vietnamese assertions unchanged, except under G6. |
| AC8 | **Catalog parity and usage.** The key-parity test covers every new key, and every key added in U3 is used by converted code. |
| AC9 | **Route modes.** With the flag off, a `next build` of the final candidate gives the same route table (static or dynamic) as a build of the U3 base. |
| AC10 | **English learning session.** On a local flag-on build, a student in English studies a topic from the first flashcard through the memory check and an exercise to the completion panel, and reviews a due card in the review sheet, seeing English interface text, locale-formatted dates and numbers, and no raw keys. |

### 1.2 Scope and non-goals

In scope:

- **Routes.** `app/(client)/learn/**`: layouts and their metadata, pages, loading states, `_components/**` (except `PendingPayments.tsx`), and the topic workspace components.
- **Actions.** `app/actions/learn-dashboard.ts`, `learning-activity.ts`, `enrolled-course-overview.ts`, `learning-workspace.ts`, `progress.ts`, `review.ts`, and `getDeckReviewCards` in `app/actions/profile.ts`. New `*-localized.ts` wrappers for the client-called actions (H4).
- **Client plumbing.** `hooks/use-card-review-queue.ts`, only to carry the message references of a saved review to its two callers; the save order, retry and drain behavior stay the same.
- **i18n wiring.** Registering the new namespace for both locales in `lib/i18n/messages.ts`, and a multi-field form of the U2 message recording in `lib/i18n/message-ref.ts` and `request-locale-result.ts` that leaves the U2 wrappers' behavior and tests unchanged (H4).
- **Helpers.** The user-visible text in `lib/memory-check.ts` and `lib/learning-activity-format.ts`, and the formatting of `formatStudyDuration`, `weekdayLabel` and `dayMonthLabel`. The learn callers of `components/learning-activity/**` (labels passed in; the component API from U2 stays).
- **Catalogs.** New keys in `messages/{vi,en}/` (H1) and their per-subtree delivery in the learn layouts.
- **Tests.** New English and locale-switch tests, and the setup-only edits G6 allows.
- **Evidence tooling.** The snapshot and scan scripts used as evidence (H6), outside the app code.

Non-goals:

- **Payments (U5).** `PendingPayments.tsx`, `lib/payment-history-format.ts` and the pending-payment data on the dashboard (decision 1).
- **Other units.** Teacher authoring and its schemas (`lib/schemas/exercise.ts`, `card.ts`), `app/actions/exercise.ts`, `review-notes.ts` and `card.ts` (U4); admin (U5); the U2 screens and the U2 parts of `profile.ts`; emails (U6); legal pages (U7).
- **Content.** Teacher-authored learning content and authored explanations, user data, code comments, logs, error codes and status values (master decision 1).
- **Behavior.** No change to scheduling (FSRS), unlock rules, progress computation, response shapes, redirects, query parameters or data. No new seed data in `supabase/seed.sql`.
- **Course initials.** `toLocaleUpperCase("vi-VN")` in `CourseRow.tsx` and `EnrolledCourseOverview.tsx` upper-cases a course title (content) and stays as it is.

### 1.3 Execution guardrails

| Guardrail | Failure if omitted |
| --- | --- |
| G1. Vietnamese strings move into the catalog verbatim, checked against the old text by the unchanged Vietnamese assertions or an exact comparison script, never by retyping. | A silent Vietnamese wording change (master invariant). |
| G2. Every action keeps its response shape, error codes, status unions and side-effect order. A message is a catalog key translated where the action returns it, and the key is recorded with `recordedTranslations` (U2 `lib/i18n/message-ref.ts`), never found later by looking the translated text up. | Clients branch differently by language, or a key reaches the user. |
| G3. Code that reacts to an error branches on a code, status or kind, never on message text. U3 adds no text-matching branch. | English messages take the wrong branch (master invariant). |
| G4. Each learn subtree receives an explicit namespace list through `ClientNamespaces`: `common`, `validation` and the namespaces its components use. A nested provider replaces its parent's messages, so each one lists every namespace its subtree needs. | A raw key reaches the user, or every learn page ships the whole catalog. |
| G5. The locale selects only text and formatting. FSRS ratings, unlock rules, redirects, cookie names, stored values and the SQL day boundary stay the same. | A tampered or English locale changes learning behavior. |
| G6. Existing tests change only in three ways: render setup moves to the shared provider (U1 helper); an import path changes when a string moves; an action mock returns its message through `recordedTranslations` when the client under test needs the key, with the same Vietnamese text; the learn-layout namespace expectations in `courses-client-boundary.test.tsx` follow the delivery that H2 sets, because that delivery is the planned change; in the U2 test `home-english.test.tsx`, the English-locale selector for the reveal button (`"Hiện đáp án"`, around line 235) and its comment change to the English label, because U3 translates that button, while the Vietnamese case (around line 215) and the four rating assertions stay unchanged. Any other changed assertion, including a source-reading test switched to catalog keys, stops the work and goes to the Owner with the replacement evidence. | Test edits hide a wording or behavior regression. |
| G7. Code outside section 1.2 stays untouched, apart from G6 setup. The shared learning components keep the props U2 gave them, and their non-learn callers render unchanged. | U3 grows into U2, U4 or U5 territory. |
| G8. With the flag off, the U1 resolver still returns `vi` without reading cookies or headers, and U3 adds no other locale read of request data. | Routes change rendering mode, or English leaks before the release gate. |

## 3. Bounded implementation hypotheses

- **H1, namespaces.** A new `learn` namespace holds the route UI (dashboard, review sheet, course overview, workspace stages, metadata, loading labels) and the action messages, registered for both locales in `MESSAGES` (`lib/i18n/messages.ts`); `learning` keeps the shared component texts and gains the activity and duration keys; `flashcard` is unchanged. Names may change while G4 and the parity test hold.
- **H2, delivery.** `learn/layout.tsx` gets `generateMetadata` from the catalog with the same title template and robots values. `(dashboard)` delivers `flashcard`, `learning` and `learn`; a new `[course-slug]/layout.tsx` delivers `learning` and `learn`; the topic layout delivers `flashcard`, `learning` and `learn`. Server components may pass translated strings as props instead where that is simpler. CP1 proves the delivery on a real build. The learn-layout expectations in `courses-client-boundary.test.tsx` change to the new lists (G6).
- **H3, server-page messages.** Actions called only from server pages translate with `getTranslations` and need no wrapper; the switch's `router.refresh()` re-renders them in the new language.
- **H4, client-called messages.** `submitQuestionAnswer`, `submitCardReview` and `getDeckReviewCards` get `*-localized.ts` wrappers on the U2 pattern. Because one result can carry several system texts, the U3 wrappers return a reference per field (for example `messageRefs: { error?, explanation?, progressError? }`, each a key with its parameters), recorded where the action chooses that text; a field the author wrote (an authored explanation) gets no reference and is shown as written. The original action result is unchanged, and the U2 single-key envelope and its tests stay as they are; the multi-field recording sits beside it in `lib/i18n/message-ref.ts` and `request-locale-result.ts`. `use-card-review-queue` passes the references of a saved review to `onSaved`. Clients hold each message as a key with parameters (`HeldMessage` or `pickServerText`) and translate it at render, so in-page text follows a switch; toasts translate when they fire (AC4). Client-built texts (review save failures, unlock and completion messages, `topic-progress-feedback`) are held the same way. Tests cover a locale mismatch for: a wrong answer with the default explanation and a `progressError`; an authored explanation with a `progressError`; and a successful `submitCardReview` with a `progressError`, in the workspace and in the review sheet. `getCourseLearningSummary` gets no wrapper, because its client caller drops failures (H3 covers its server callers, the U2 one included, whose call stays unchanged).
- **H5, formatting.** The existing one-argument `formatStudyDuration`, `weekdayLabel`, `dayMonthLabel` and `formatRelativeDay` keep their signatures and Vietnamese output for existing callers. U3 adds locale-aware forms beside them (like U2's `translateRelativeDay` beside `formatRelativeDay`) that take a translator or locale and use catalog plurals or `lib/i18n/format.ts`, and the learn screens call those. Counts shown in U3 screens (for example `dueCardCount`) go through `formatCatalogCount`. CP1 records today's `vi` output for a fixed input set first and checks that the new forms give the same `vi` output, and that `1234` shows as `1234` in `vi` and `1,234` in `en`.
- **H6, evidence tooling and data.** The snapshot and scan scripts are rebuilt on the U2 approach in the session scratchpad, outside the app code: they read visible text, accessible names, title, description and `lang` with reduced motion. The raw-key check takes its namespace list from the catalog files and tests every line on its own, whether or not the line also holds Vietnamese. Student data comes from the seed course `b2-qa-in-progress` and from the matrix and review-session fixtures on the isolated stack. Rating a card or answering a question writes the learner's progress, so before each capture run (base and candidate, each width) the fixture learner's progress is reset in the fixture's own scope (the `resetLearner()` pattern of `learning-topic-completion.smoke.spec.ts`), and the same action sequence then opens each state. Each state has a marker that proves it opened and tells the states apart (a card word, the locked panel, a question, a correct and an incorrect answer, the completion panel). CP1 records the slugs, the reset step and the markers. Owner QA uses the local seed on a flag-on build, as in U2 decision 3; if the seed lacks a due review card or a completable topic, CP1 reports it and the Owner chooses the data.

## 5. Risks, rollout and rollback

| Risk | Mitigation |
| --- | --- |
| A Vietnamese string changes while moving. | G1, the unchanged Vietnamese assertions (AC7) and the AC1 snapshot pairs. |
| A nested provider drops a namespace and a raw key reaches the user. | G4, the CP1 real-build check and the AC2 raw-key scan; render tests alone cannot catch it. |
| A learner sees an old-language message after switching, or an answer error disappears. | AC4 and H4 reuse the U2 mechanism, with locale-switch and cross-tab tests. |
| Translating a message changes unlock, scheduling or progress behavior. | G2 and G5; the action and integration tests keep their codes and shapes. |
| Changing the shared activity component or `getCourseLearningSummary` alters the U2 course detail. | G7: only the learn callers pass labels, and the U2 caller of `getCourseLearningSummary` keeps its call; the public course detail tests stay unchanged and the CP2 snapshot pair includes the enrolled course detail. |
| The snapshot comparison compares the wrong learning state. | H6 markers per state, recorded at CP1. |
| The workspace checkpoint is too large to review. | CP3 and CP4 split it by stage. |

- Rollout runbook: none. The flag stays off in production, so merging changes nothing visible.
- Stop when: a Vietnamese assertion must change beyond G6; an AC1 pair differs; the route table changes with the flag off; a learn caller cannot receive translated labels without changing a shared component's behavior; the scope would cross into U2, U4 or U5 files beyond section 1.2.
- Rollback: revert the PR. No data or hosted configuration changes.
