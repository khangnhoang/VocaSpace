# Master plan — Initial dependency modernization

Progress: [progress.md](./progress.md). Problems: [problems.md](./problems.md). Add a detail plan under `implementation-plans/u<n>-<slug>/plan.md` when opening each unit.

## 1. Goal and outcome

- Goal: Deliver a finite update of the existing dependency inventory and align VocaSpace on a supported Node LTS across local development, CI and new production deployments, with Node 26 as the first trial candidate. Establish a verified baseline for recurring Dependency Maintenance.
- Outcome 1: Every direct dependency and relevant transitive finding on the refreshed baseline has an evidence-backed disposition. Confirmed security findings are prioritized by product runtime, build/install or tooling exposure.
- Outcome 2: Selected compatible security and ownership fixes ship. Local, CI and deployed production evidence demonstrates the same accepted Node major, with compatible npm and matching Node types.
- Outcome 3: Selected compatible updates ship in independently verifiable batches. A closing audit identifies what changed and assigns an owner, rationale and reopening condition to every deferred finding or package group.
- Size and risk: Large. Framework, validation, auth SDKs and test tooling cross different verification and rollback boundaries, and Node alignment touches the deployment pipeline.

## 5. Order and rollout gates

1. Refresh the audit before the first batch. U1 and U2 trials can proceed independently. Order their releases by confirmed exposure and trial-proven prerequisites. U2 can ship first if it addresses the higher-impact path and has no U1 prerequisite. Try Node 26 when U3 opens, before its rollout work. Other units may proceed on the current runtime when their candidates support it. Require U3 evidence only for candidates that need the aligned runtime. Coordinate overlapping manifest and lockfile work and refresh each batch's base before review.
2. Before push, resolve candidate-caused blockers found in the trial and rerun affected checks against the final change. Compare advisory IDs and resolved paths in full and omit-dev audits for security batches. Before merge, use the existing required CI jobs and Preview on the reviewed revision. Confirm that Vercel requires `production-gate` for production, automatic domain assignment follows the release SOP, and the authorized merge covers automatic production release. Use local evidence for reproducible checks and hosted evidence for Linux CI and Vercel-specific behavior. Reuse existing commands, fixtures and workflows. Add a check only when an identified regression cannot be covered by them. Confirm the recovery target under the SOP. If recovery would restore an affected version, obtain the Owner's recovery decision. Exercise rollback only with its own authority.
3. After merge, observe production-gate on the merge revision. On failure, confirm the domain is still on the serving revision and investigate the failed gate. Once the domain moves, match it to the intended revision and build metadata, repeat the Node runtime observation for U3, and run bounded read-only smoke. Use that evidence to retain the release or request recovery. After recovery, recheck the domain, revision, runtime and smoke.
4. Close delivery once selected batches and Node alignment are verified in production. Reconcile every remaining advisory path from the closing audits, including paths outside selected batches or absent from the problem tracker. For each deferred path, record a named owner, rationale and reopening condition. Resolve or transfer open delivery issues to an existing tracker. Keep the final inventory, audit evidence and residual dispositions in the delivery record so recurring Dependency Maintenance can adopt the baseline when its charter is published under separate authority.

## 6. Program risks

| Risk | Mitigation |
| --- | --- |
| Registry or lockfile drift changes the candidate after a trial | Pin the reviewed resolution through the lockfile, run a clean install and compare advisories and resolutions before review. |
| Current imports work only because another tool supplies the package | Check actual resolution and declare ownership before removing or moving the provider. Exercise validation and test configuration from a clean install. |
| An SDK or framework update preserves types but changes runtime behavior | Use existing contract and smoke tests for auth/session, learning, authoring or payment where touched. Keep each deployment and recovery boundary small. |
| Local, Linux CI and hosted Node versions differ despite configuration changes | Capture the observed version in each environment, including deployed runtime evidence. |
| Audit totals reward reclassification while exposure stays open | Compare advisory IDs, resolved paths and actual use. Hand off residuals with explicit exit conditions. |

## 7. Out of scope

- Recurring review execution, automation and ownership migration into the evergreen charter.
- Feature changes, framework replacement, unrelated refactors or database changes.
- Bulk upgrades to latest, unapproved major migrations and changing global CI/CD or security policy.
