Revision: r2, 2026-10-11 (Codex r1 findings R1–R4, S5, S6 applied; Codex r2 PASS). Owner approval: approved 2026-10-11. Master plan: [plan.md](../../plan.md) (Decision 27).

## 1. Binding Spec

### 1.1 Outcome and acceptance

Outcome: after this unit merges and its separately authorized hosted steps run, learner content reads no longer evaluate the topic read check through a scan of unrelated topics, the memory check of a topic with active flashcards opens only after the learner has rated every active card at least once (enforced in the database and shown in the workspace), free enrollment no longer navigates away on its own, the stage thread shows a finished stage as done while the learner is on it, and the LF2 closeout and the related `problems.md` entries are reconciled.

### 1.2 Scope and non-goals

- In scope: a migration replacing the ancestor joins of the five learner child-content `SELECT` policies (`cards`, `exercises`, `question_groups`, `questions`, `question_options`) with per-parent checks, keeping the `topics` policy predicate, and, only when the AC2 local measurement shows the topic read check itself still dominates, a further migration that folds `private.q7_can_read_topic`'s helper calls into fewer queries with the same result; a migration adding the cards-seen condition to the memory-check answer write path (policies and answer RPC); the action, schema, workspace and memory-stage changes for AC5/AC6; the enrollment-card and stage-thread changes for AC7/AC8; tests and the CI integration split for new isolated-runtime suites; program docs; separately granted hosted steps.
- Non-goals: changing who can read anything (AC3); changing the LF1 flashcard-done rule, D4 completion rules, grading, FSRS or the exercise memory gate; optimistic UI; further card-action latency work (recorded, §1.4 Q4); moving card writes off the Data API; Preview changes; the chapters/courses policies and Storage media policies; `STUDENT-003`, `QUALITY-001`, the auth follow-ups, the teacher reorder lock order, D5, D9; creating production content, markers or progress resets.

| Guardrail | Failure if omitted |
| --- | --- |

| G2. A per-parent read helper is `SECURITY DEFINER`, `set search_path = ''`, schema-qualified, `STABLE`, takes only the parent id (the actor comes from `auth.uid()` inside `private.q7_can_read_topic`), revokes `PUBLIC` and `anon`, grants execute only to the roles that read through the policy, and returns exactly the old predicate: the parent rows are not removed on every level the old policy checked, and `private.q7_can_read_topic` of the owning topic is true. | A definer helper that drops a `removed_at` check or takes a caller-supplied user id exposes removed or other learners' content. |
| G3. | G4. The cards-seen condition has one SQL definition, used by the answer write policies and inside the answer RPC's write statement on both the insert and the `ON CONFLICT DO UPDATE` branch (as LF2 G9 does for the memory gate). | G5. | G6.   - Free enrollment: stay on the page and offer `Bắt đầu học` instead of navigating automatically.
  - No separate LF2 closeout PR; its docs ride in LF3.
- Further Owner answers, 2026-10-11:

  - Q2. `LEARNING-INTEGRITY-001`: read-only hosted catalog check of the L1 constraints, policies and grants at rollout under a grant; the rolled-back `authenticated` allowed/denied smoke only if the Owner grants it then; without the smoke the entry stays open.

### 1.5 Measurement method (AC1, AC2, G3)

- Local runtime: the isolated runtime (45441) after `db reset`, seeded by a committed deterministic fixture script (fixed ids and counts: at least 200 topics over 20 courses, the target topic with 30 cards, 10 exercises × 10 questions × 4 options and a memory-check set, one enrolled learner); then `ANALYZE` on the content, enrollment and membership tables; the row counts of `topics`, `cards`, `exercises`, `question_groups`, `questions` and `question_options` are recorded.
- Statement capture: statement (a) is a PostgREST read of one question's options; statement (b) is the `getLearningWorkspace` topic request. Their exact SQL is taken from the isolated runtime's Postgres log (`log_min_duration_statement = 0` for the capture only) while a supabase-js script issues the request as the fixture learner.
- Execution: in one transaction as `postgres`, `set local track_functions = 'all'`, then `set local role authenticated` and `set local request.jwt.claims` to the learner's claims, run the statement, then read `pg_stat_xact_user_functions` for `private.q7_can_read_topic` and any new helper; that delta is the call count. `EXPLAIN (ANALYZE, BUFFERS)` is run separately for the plan shape. Timing: 3 discarded warm-up runs, then the median of 20 runs.
- Production metric, named "topic page document response time": on the deployed topic page, n ≥ 10 hard reloads (cache disabled in DevTools, first load discarded), recording `responseStart - requestStart` and `responseEnd - requestStart` from `performance.getEntriesByType('navigation')[0]`; client-side (RSC) navigations and prefetches are excluded. A console script for it is prepared in CP1.

## 2. Repository facts

Baseline: `fc8abde` (main after PR 146), checked 2026-10-11.

- `20260923143029_q7_topic_read_and_private_media.sql`: the `topics` policy is `removed_at is null and private.q7_can_read_topic(id)` with no ancestor join; of the five child policies, the `cards` and `exercises` policies are `exists (select 1 from topics t where t.id = <row>.topic_id and private.q7_can_read_topic(t.id))`; `question_groups` and `questions` join `exercises` and `topics`; `question_options` joins `questions`, `exercises` and `topics`. Each joined table's own RLS policy applies inside the subquery for the invoker — justifies the per-parent change and AC3.
- `private.q7_can_read_topic` (same file) is `SQL STABLE SECURITY DEFINER`, already requires the topic row to exist with `removed_at is null`, and calls `has_course_content_read_access`, `is_admin`, `d1_topic_group_member` and `has_topic_review_access` — justifies G2 (the outer `topics` join adds nothing) and Q5.
- LF2 hosted `EXPLAIN` (LF2 plan §2): the `question_options` policy plans as a hashed subplan with `Seq Scan on topics` filtered by the topic read check; preview timing shows the question context query at about 400 ms hosted versus about 55 ms locally — justifies AC1/AC2.
- `getLearningWorkspace` (`app/actions/learning-workspace.ts`) loads the topic with embedded `cards`, `exercises`, `questions`, `question_options`, `question_groups` and the memory-check set in one query, does not read `user_flashcards`, and fails the page when the query errors; LF2 answer actions go through a definer RPC and no longer read these tables through RLS — justifies measuring the page load, not the actions.
- `private.lf2_memory_gate_open` (`20261010120000`) returns true for a memory-check question and the D4 `memory_check_done` flag for an exercise question; it is AND-ed into both `User_answers` `WITH CHECK`s and used in `lf2_submit_question_answer`'s precheck and write — justifies G4/G6.
- `private.d4_topic_completion_state` (`20261010090000`) counts active cards as `topic_id` match and `removed_at is null` — justifies G5.
- `user_flashcards` rows are written by the app only through `lf2_submit_card_review` (invoker), but the L1 `User_flashcards - Auth Insert`/`Auth Update` policies (`20261008130544`) also allow a direct authenticated write of the learner's own row; in the product rows are removed only by cascade (tests delete with the service role); card removal is soft; `unique_user_card (user_id, card_id)` (remote schema baseline) prevents duplicate rows, so per-card counting is a safety property, not a live case; `User_flashcards - Active Admin Select` (`20261007100000`) lets an active admin read every learner's rows — justifies "own row exists" as the condition, the explicit `user_id` filter (G4).
- Public Preview answers go through the service-role `get_public_course_preview_answer` and never touch the `lf2_*` helpers — justifies AC6's Preview clause.
- `PublicCourseEnrollmentCard.tsx` calls `continueLearning()` (first-topic navigation) after a free enrollment and in the paid `onSuccess`; `__tests__/components/public-course-detail.test.tsx` asserts that navigation — justifies AC7 and Q1.
- `LearningWorkspace.tsx` `stageSteps` gives `current` precedence over `done` for all three steps — justifies AC8.
- `MemoryCheckStage.tsx` ignores `errorCode` and shows the message only — justifies AC5.
- `private.lf2_answer_precheck` classifies `unavailable → not_enrolled → option_unavailable → memory_locked → ok`, and its `memory_locked` branch applies only to exercise questions; `lf2_submit_question_answer` calls it before the write and again to reclassify a 0-row write — so the new status must come from both the initial classification and the 0-row reclassification for memory-check questions.
- `LearningWorkspace.tsx` builds the flashcard queue once from the loaded cards (`useState(flashcards)`, `restartFlashcards`), so a card added after page load never enters the queue without a fresh load — justifies the AC5 recovery clause.
- `.github/workflows/ci.yml` excludes the isolated-runtime suites from the main integration run and runs them in a separate step on port 45441 — justifies G8.

## 3. Bounded implementation hypotheses

- Per-parent helpers such as `private.q7_can_read_exercise(uuid)` and `private.q7_can_read_question(uuid)`; `cards` and `exercises` call `private.q7_can_read_topic(topic_id)` directly — may change if G2 and AC3 hold.
- The cards-seen condition as a new private helper used by an updated `private.lf2_memory_gate_open` (same name and signature, so the policies need no change) or by an extra `AND` — may change if G4–G6 hold.
- A new precheck/RPC status (for example `cards_locked`) for memory-check questions at the `memory_locked` position (after `option_unavailable`), returned by the initial classification and the 0-row reclassification, mapped to a new code in `lib/memory-check.ts` and `lib/schemas/learning-workspace.ts` — may change if AC5 and G7 hold.
- The workspace flag computed from an own-row `user_flashcards` read (`card_id` and `last_rating`, filtered by `user_id`, counted per distinct card so duplicates follow LF1's `EXISTS` semantics; it gives both cards-seen and the number of cards still needing `Ổn`/`Dễ`) added to the loader, and updated client-side as cards are rated; recovery after `cards_locked` by a full reload or a remount keyed on fresh server data — may change if G4, G7 and AC5 hold.
- Enrollment card: a local "just enrolled" state chooses `Bắt đầu học`; `router.refresh()` keeps the server DTO current — may change if AC7 holds.
- Stage thread: a step carries `done` and `current` together — may change if AC8 holds.

## 5. Risks, rollout and rollback

| Risk | Mitigation |
| --- | --- |
| A per-parent helper changes a read boundary | G1/G2 and the AC3 matrix on the baseline first |
| Planner still evaluates the check per unrelated row | AC2 reports plan shape and `pg_stat_xact_user_functions` call counts separately from time |
| Learners mid-memory-check when the gate ships are blocked until they rate the remaining cards | Intended (Owner); the locked panel routes to the cards; existing answers stay |
| A card added later closes an already started memory check | Intended (Owner); exercises stay open when the memory check was already passed |
| Deployed app does not know the new RPC status, or the new app meets the old database | G7: app first, only existing tables on the read path, both version pairings tested before merge |
| Production page load is dominated by other work and does not improve | Reported with numbers (AC2); not hidden |

- Rollout runbook: (1) merge and wait for the production deploy READY; (2) push the LF3 migrations (grant); (3) read-only catalog and `EXPLAIN` checks (grant); (4) L1 catalog check and optional rolled-back smoke (grant, Q2); (5) Owner page-load measurement and learner journey; (6) docs follow-up commit on the next PR or this branch before merge as the State requires.
- Stop when: the AC3 matrix fails after the policy change; a hosted step lacks its grant; the hosted migration history differs from the repository; a rollout order other than G7 is needed.
- Rollback: each migration has a down script in `supabase/rollbacks/`; restoring the Q7 policies and the LF2 gate body is lossless because no data is changed. UI changes revert with the code.
