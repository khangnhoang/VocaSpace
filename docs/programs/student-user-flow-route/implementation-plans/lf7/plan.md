## 1. Binding Spec

### 1.1 Outcome and acceptance

Outcome: after this unit merges, every course-structure write the app makes takes its locks in one order, so two teachers changing the same course at the same moment through the app wait for each other instead of one of them getting a deadlock error (STRUCTURE-LOCK-001). Two residual paths keep the old order and are accepted, not fixed: a direct `update chapters set title` by a client outside the app (the column grant stays, AC2), and the production app before this PR during the short window between the hosted push and the deploy (§5). Either can still deadlock with a course-first app write, and Postgres may abort either side. `npm run lint` reports 0 errors on the repository and CI runs it, so a new lint error turns CI red (QUALITY-001). The program docs record the LF6 merge.

The one lock order (the "course order"), used by every function in AC1: the course advisory lock `pg_advisory_xact_lock(hashtext(<course_id>::text))` first, then the `courses` row, then `chapters` rows, then `topics` rows, each only when the function needs it. Re-taking the course advisory lock later in the same transaction (for example in a trigger) is harmless.

### 1.2 Scope and non-goals

- In scope: AC1–AC8, the migration's down script in `supabase/rollbacks/` (as LF2 and LF3 did), and updating tests that mock `updateChapter`'s direct update.
- Non-goals:
  - changing any structure function that already follows the course order, or any trigger;
  - the advisory key space (course and topic ids share one `hashtext` key space; not changed);
  - non-structure lock paths (moderation, content edits, payment);
  - other lint rules, `--max-warnings`, or ESLint config beyond the three ignores;
  - `PERF-ACTION-001`, `AUTH-022`/`AUTH-023`, any learner UI.

## 2. Repository facts

Baseline: `main` at `971702e` (LF6 merge).

- Structure functions that already take the course advisory lock first (latest definitions): `create_topic_ordered` (`20260924110000_d2_preview_quota_lifecycle.sql:1100`, lock `:1120` then chapter row `:1125`), `hide_chapter(uuid, uuid[])` (`:819`, lock `:840`, course row `:842`, chapter row `:845`), `restore_chapter_ordered` (`:1019`, lock `:1038`, course row `:1040`, chapter row `:1043`), `d1_delete_topic` and `d1_restore_topic` (through `d1_lock_topic_lifecycle`: course lock, topic lock, topic row).
- Inversions (static reading of the SQL, not yet shown by a test):
  - topic moves hold the chapter row and wait for the course lock, while `hide_chapter`, `restore_chapter_ordered` or `create_topic_ordered` hold the course lock and wait for the chapter row;
  - chapter move and create hold the `courses` row and wait for the course lock (taken by `d1_guard_chapter_mutation` at the chapter write), while `hide_chapter` or `restore_chapter_ordered` hold the course lock and wait for the `courses` row;
  - `updateChapter` updates `chapters.title` directly (`app/actions/chapter.ts:351-357`): the UPDATE locks the chapter row, then the trigger takes the course lock, while `hide_chapter` or `restore_chapter_ordered` hold the course lock and wait for the chapter row.
- `d1_guard_chapter_mutation` (`20260915100000_d1_trusted_lifecycle.sql:387-454`) runs `before insert or update or delete on chapters` for user callers and takes the course lock; `d2_guard_chapter_identity` (`20260924100000_d2_chapter_creator_authority.sql:153-184`) blocks direct inserts and protected-field updates. `authenticated` holds only `update (title)` on `chapters` (`:210-212`).
- `d1_guard_topic_lifecycle_mutation` (latest `20261001100000_structure_topic_pending_reorder.sql:11-56`) takes course lock, topic lock, topic row on topic writes; with every structure path holding the course lock first, these are serialized behind it.
- Concurrency test pattern: `course-preview-quota.test.ts:961-1091` holds a lock in a `psql` transaction and polls `pg_locks`, including the `classid`/`objid` split of the `hashtext` key. No test races the structure RPCs today.
- Lint: `npm run lint` is `eslint` (flat config). On the planning machine it reported 5288 problems, almost all in the gitignored `.next-e2e`, `test-results` and `.playwright-cli`; tracked files have 7 errors and 11 warnings (listed in AC6). CI has no lint step today.

## 3. Bounded implementation hypotheses

- Migration `<timestamp>_lf7_structure_lock_order.sql`: `create or replace` the four functions and add `rename_chapter`. For topic moves: `select t.chapter_id`, then `select c.course_id from chapters` (no lock), take the course lock, then `select … from chapters where id = … and course_id = <read course> for update` (not found → `CHAPTER_NOT_FOUND`), then the existing checks and target lock (the existing `t.chapter_id = v_chapter.id` re-check stays). For chapter move and create: take the course lock on the read course id before the existing `courses … for update`. A short Vietnamese comment states the course order once.
- `rename_chapter`: same shape as `move_chapter_order`'s prologue, then `update chapters set title = v_title where id = … returning …`.
- Down script: restores the previous definitions from their latest files, and drops `rename_chapter`.
- AC4 tests: one new file (for example `__tests__/integration/structure-lock-order.test.ts`) reusing `beginLocalPostgresTransaction`, the new in-transaction statement function and the `pg_locks` wait from `course-preview-quota.test.ts`; the write goes through the teacher's Supabase client so it has its own backend.

## 5. Risks, rollout and rollback

| Risk | Mitigation |
| --- | --- |
| A redefined function drifts from its latest body | G1 and the AC5 suites |
| A test proves nothing | G2: each AC4 test fails on the baseline for the inversion reason |
| A lint fix changes payment behaviour | G3: type-only changes |

- Rollout: the migration is compatible with the app before and after this PR (same RPC contracts, `rename_chapter` only added, grants unchanged), and production `updateChapter` needs `rename_chapter` on hosted. So, with a separate Owner grant, the migration is pushed to hosted after CI is green and before the merge, then verified read-only (the four function definitions take the course lock first, `rename_chapter` exists with execute for `authenticated` only); then merge and the production deploy. Root 45321 gets the migration only when the Owner asks (`supabase migration up --local`, no reset).
- Stop when: a fix needs a signature, error-code or authority change; a function cannot take the course lock first without a new error path; a lint fix needs a runtime change in payment code. Report to the Owner.
- Rollback: revert the PR and confirm the previous app is deployed; only then run the down script on hosted (Owner grant), since the down script drops `rename_chapter` that the LF7 app calls.
