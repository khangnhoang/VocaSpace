## 1. Binding Spec

### 1.1 Outcome and acceptance

Outcome: `/login`, `/register` (with its check-email step), `/forgot-password` and `/auth/set-password` share one Product Language auth shell. A form column sits beside a panel that illustrates the FSRS memory curve and reacts to the form. Registration shows a truthful progression rail, and the forms gain a password kit, email help, a remembered sign-in method and a return to the protected `/teacher`, `/profile` or `/admin` page the proxy guarded. Server rules, neutral messages and fixed post-verification paths stay as they are. AUTH-012 closes.

The Owner accepted the direction of the rendered demo [sources/index.html](./sources/index.html) on 2026-11-09, amended by §1.4. Where the demo and §1.4 differ, §1.4 wins. The demo's sample data, its simulated network delays, the "Demo:" buttons, the purple demo control bar and its simplified header are not part of the design.

### 1.2 Scope and non-goals

- In scope:
  - Pages and components: the four auth routes and their client components, a shared auth shell, panel and curve components, and a route group layout for the three `(client)` auth routes.
  - Server contract: `signInUser`'s success result, `/auth/callback`'s destination, the proxy's return-path cookie write (AC7), and the last-method cookie written by the action and the callback (AC6), all through one helper module and its schema.
  - Copy and existing components: the label "Tiếp tục với Google" in `GoogleSignInButton`.
  - Tests and docs: the directly affected unit, component, route and smoke tests, including `e2e/support/auth.ts`. The G1 wording in the auth-onboarding plan, AUTH-012 and this program's progress.
- Non-goals:
  - Auth contract: changes to `signUpUser`, `resendSignupConfirmation`, `requestPasswordRecovery` or `setPasswordAfterConfirmation` beyond their callers' UI; `/auth/confirm`; the password rule; schemas other than the new return-path helper; a new route or query parameter.
  - Data and email: DB, RLS or migrations; email templates (FEAT-017).
  - Other screens: `/profile`, the header and mobile account sheet, shared `Input`/`Button`/`Card` primitives.
  - Product features: magic-link sign-in; optional phone/date-of-birth/gender at sign-up; a post-sign-up "account ready" page; returning to `/learn` ([FEAT-025](../../future-features.md#feat-025)), to a query string or to public pages; dark theme; new packages or fonts; any `/privacy` or `/terms` wording.

### 1.3 Execution guardrails

| Guardrail | Failure if omitted |
| --- | --- |
| G1. The return path comes only from the cookie the proxy writes on its own signed-out redirect. It is never read from a query, hash, form field or `Referer`, and nothing else writes it. Both the write and the read validate it: it is a pathname under `/teacher`, `/profile` or `/admin` (segment-bounded) and starts with exactly one `/`. It may not contain `//`, `\`, `..`, control characters or encoded `/`/`\`, and it is at most 512 characters. Anything else yields `/`. Redirects use a relative `Location`, as `/auth/callback` does today. | An attacker-supplied value turns sign-in into an open redirect or phishing hop, or an absolute redirect switches host and drops the new session cookie. |
| G2. The return-path cookie is `HttpOnly`, `SameSite=Lax`, `Path=/` and `Max-Age=600`. It is `Secure` when the request arrived over HTTPS, decided from the request protocol, not `NODE_ENV`. The proxy and `/auth/callback` use `request.nextUrl.protocol`. `signInUser` has no request object, so it uses `x-forwarded-proto` from `headers()` and falls back to the scheme of the `Origin` header. Every successful email sign-in and Google callback deletes it. | Scripts read it, a stale value redirects a much later sign-in, or the CI production build on `http://127.0.0.1` drops the cookie. |
| G2b. The return path is written only on the proxy's redirect for `/teacher…`, `/profile…` or `/admin…`; never on a pass-through response and never for `/learn` (decision 14). | Production link prefetch runs the proxy without exposing the prefetch headers, so a pass-through write would record a page the visitor never opened and send an ordinary sign-in there. |
| G3. `/auth/confirm`, sign-up, recovery and `/auth/set-password` keep their fixed destinations (A1 G1, G8). | A freshly verified or recovering user is sent somewhere other than the password step. |
| G4. Server actions keep their inputs, Zod schemas, neutral results (A1/A2 G5), cooldowns, sign-up gate and password-setup eligibility. The only server changes are the AC6/AC7 cookies and `signInUser` returning the validated destination. | Account enumeration, a sign-up bypass or an auth regression. |
| G5. The last-method cookie holds only `email` or `google` and carries no identifier (decision 12). It is `HttpOnly` (read on the server), `SameSite=Lax`, `Path=/`, `Max-Age` 180 days and `Secure` under the G2 rule. Any other value is treated as absent. | Personal data is stored outside what `/privacy` §3 discloses, or a tampered value breaks the page. |
| G6. The legal consent notice keeps its Owner-approved text and links. | Unapproved legal wording ships. |
| G7. Colors, type, radii and elevation come from Product Language. The `#64748B` input boundary and the focus styles apply at the auth usage sites. Shared primitives stay unchanged. | Other screens change, or AUTH-012's 3:1 acceptance fails. |
| G8. The panel is an illustration labelled "Minh hoạ" and shows no counts, users or claims beyond the curve. | The page presents fabricated statistics. |
| G9. Accessible names follow the visible Vietnamese labels. `e2e/support/auth.ts` and every smoke spec that signs in through the form change in the same checkpoint. This supersedes the A1 G9 aria-label contract. | The smoke suite breaks, or names fail WCAG 2.5.3 Label in Name. |
| G10. Forms and their content are visible in the server HTML before hydration, and motion never starts content hidden. No credential or email form can submit natively as a GET before hydration: each form uses `method="post"` with no URL-bearing fallback, or keeps its submit control disabled until hydration. A test on the server-rendered markup proves it. | A slow or failed hydration leaves an empty auth page, or a pre-hydration submit puts the password into the URL, history and server logs. |
| G11. The proxy keeps today's redirect destinations and query handling: `/profile` and `/admin` drop their query, `/teacher` keeps it, and every redirect sets `reason`. The return-path cookie is additive. | The A5 decision on `/profile` and `/admin` regresses. |
| G12. Any design change beyond the accepted demo and §1.4 is asked of the Owner first. | The Owner's accepted design is silently changed. |

## 2. Repository facts

Baseline: `ab809e8`, checked 2026-11-09.

- **Auth surfaces today.**
  - `/login`, `/register` and `/forgot-password` are client pages under `app/(client)`, whose layout renders the site header.
  - `/auth/set-password` is a server page outside `(client)`, with no header, that guards on `getPasswordSetupEligibility` and renders `SetPasswordForm`.
  - All of them use a small centered `Card` with mixed Blue 400/white headers.
  - This justifies AC1, AC2 and AC11.
- **Open AUTH-012** (`docs/programs/ui-ux-design/problems.md`): auth screens have no accepted design; input boundaries measured 1.26:1 and focus 2.59:1; "Quên mật khẩu?" should move to the right edge; the exit condition is the redesign PR meeting 3:1 on all auth screens. Justifies AC3, AC14 and G7.
- **Fixed-path G1.** auth-onboarding invariant G1 (`docs/programs/auth-onboarding/plan.md` §4) and A1 G1 bind fixed redirect paths. `/auth/callback` and `/auth/confirm` redirect only to constants with a relative `Location`. `utils/supabase/middleware.ts` redirects signed-out `/teacher`, `/profile` and `/admin` requests to `/login` with `reason=signin_required`: it drops the query for `/profile` and `/admin` and keeps it for `/teacher`. The `/learn` pages redirect to `SIGN_IN_REQUIRED_LOGIN_PATH` themselves. Justifies decision 10, G1–G3, G11 and AC7.
- **Cookie writes.** Next.js 16.3.8 allows cookie writes in proxy, Server Functions and Route Handlers but not during Server Component rendering (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/cookies.md`). The `/learn` pages therefore cannot write the return path themselves. Justifies G1 and decision 14.
- **Prefetch.** The proxy matcher (`proxy.ts`) runs on every page request, prefetches included. Next strips `next-router-prefetch` and `rsc` from the request seen in proxy (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`, "RSC requests and rewrites"). The header shows the "Học tập" link (`/learn`) to every visitor (`components/ui/header-nav.tsx`), while links to `/teacher`, `/profile` and `/admin` render only for signed-in users. CI runs E2E on a production build (`E2E_WEB_SERVER=start`, `.github/workflows/ci.yml`), where links prefetch; `next dev` does not prefetch. Justifies G2b, decision 14 and the production-build smoke in CP2.
- **Native submit.** The four auth forms are `<form onSubmit=…>` without `method` or `action` while React Hook Form gives their inputs `name` attributes, so a submit before hydration is a native GET carrying the values in the URL. Justifies G10.
- **Current sign-in behavior.** `signInUser` returns `{ success: true }` or the fixed `SIGN_IN_FAILED_MESSAGE`. The login page then toasts and pushes `/` after a 1 s timeout. The proxy sends signed-in visitors of `/login` and `/register` to `/`. Justifies AC3 and AC7.
- **Server-side setup flows.** `/auth/set-password` serves first-time setup after sign-up, recovery, and accounts an admin created (A5 reuses the recovery email). Eligibility distinguishes first setup from recovery but not self-sign-up from admin creation. Justifies decision 11.
- **Login form contract.** A1 G9 pins the login inputs to `aria-label="Email"`/`"Password"` and the button to `"Sign in"`. `e2e/support/auth.ts` and 8 smoke specs log in by those names, and `__tests__/components/auth-onboarding.test.tsx` asserts them. Justifies G9.
- **Google button.** `GoogleSignInButton` is labelled "Đăng nhập bằng Google" (A4 decision 1), which `__tests__/components/google-sign-in-button.test.tsx` asserts. The Google provider is disabled locally (`supabase/config.toml`) and unsupported on preview deployments (A4 decision 3). Justifies decision 13 and the production check in §5.
- **Privacy text.** `/privacy` §3 says VocaSpace uses cookies to keep the session and to remember interface state, and the page comment requires a same-PR update for new cookies outside that disclosure. Justifies decision 12 and G5.
- **Existing tests.** `__tests__/components/auth-onboarding.test.tsx` covers register steps, check-email cooldown, login notices, forgot-password neutrality and duplicate-submit locking, and set-password validation. The proxy, callback and action suites are `__tests__/proxy.test.ts`, `__tests__/utils/supabase-middleware.test.ts`, `__tests__/actions/auth-callback-route.test.ts` and `__tests__/actions/auth.test.ts`. These contracts change only where this plan says, and are updated, not weakened.
- **Installed tooling.** Motion for React is installed. The homepage uses `LazyMotion`/`domMax` for a shared indicator, and U2 uses `MotionConfig reducedMotion="user"`. Plus Jakarta Sans and Geist are loaded. Justifies AC13 without a new dependency.
- **Local QA support.** The local stack has email confirmations on and Inbucket on port 45324. The seed has `student@gmail.com`, `teacher@gmail.com` and `admin@gmail.com`. Justifies the QA fixture section.

## 3. Bounded implementation hypotheses

- **Route group and shell.** A route group `app/(client)/(auth)/` with `layout.tsx` holds `login`, `register` and `forgot-password` without changing URLs. The layout renders a client `AuthShell` that keeps the panel mounted, derives the view from `usePathname` plus a small context the register flow updates, and reads the last-method cookie server-side so AC6 holds at first paint. `/auth/set-password` renders the same shell without tabs. Component paths may change if AC1, AC2, AC6 and G10 hold.
- **Return-path helper.** `lib/auth/return-path.ts` owns the cookie names, a Zod-backed `parseReturnPath` and the allowlist, used by proxy, action and callback. It may change if G1, G2 and G5 hold.
- **Proxy write.** The proxy sets the return-path cookie on the redirect response it already builds for signed-out `/teacher`, `/profile` and `/admin` requests, from `request.nextUrl.pathname`. This may change if G1, G2, G2b and G11 hold.
- **Sign-in consumers.** `signInUser` reads and deletes the return-path cookie, writes the last-method cookie and returns `{ success: true, redirectTo }`. The page then calls `router.replace(redirectTo)` and `router.refresh()`. `/auth/callback` does the same for Google with a relative 303. This may change if AC3, AC6, AC7 and G1–G4 hold.
- **Curve module.** The curve math lives in a pure module (for example `lib/auth/memory-curve.ts`) producing path data per variant, with unit tests for the FSRS formula and the 90% review points. Drawing uses Motion `pathLength`, nodes scale in, and the flashcard flip uses Motion `rotateY` or a CSS 3D transform. This may change if AC12, AC13 and G8 hold.
- **Register steps.** The register page splits into step components under `register/_components/`, each step its own `<form>` so Enter submits that step. ## 5. Risks, rollout and rollback

| Risk | Mitigation |
| --- | --- |
| The return path becomes an open redirect through an encoding or path-normalization gap. | G1 allowlist on write and read, relative `Location`, the CP1 rejection matrix and an independent review of CP1 before later checkpoints build on it. |
| Production prefetch runs the proxy for links a visitor never opens. | G2b writes only on the proxy's own redirects for routes whose links render only to signed-in users; the CP2 production-build smoke proves an ordinary sign-in still lands on `/`. |
| Changing the login names breaks smoke specs owned by other programs, including the specs that sign in through `e2e/support/auth.ts`. | G9: every affected spec and the shared helper change in CP2; the whole smoke suite runs there on a production build and again at Final. |
| The shell's route group or layout changes test imports. | Hypothesis-level; tests import the new paths. `/login` is already dynamic because the server `Header` reads the session, so reading cookies adds no rendering cost. |
| Google return-to cannot be exercised before production. | Route tests in CP1; after merge the Owner signs in with Google from a signed-out `/profile` and confirms the landing page. |
| Motion delays or hides forms on slow devices. | G10 and AC13; CP4 checks with reduced motion and rapid input. |

- Rollout runbook (Owner or hosted steps, in order): CI green on the PR → independent review PASS → Owner reviews the running screens → merge → on production, the Owner checks email sign-in from a signed-out `/profile` (lands on `/profile`), an ordinary sign-in after browsing the homepage and `/courses` (lands on `/`), and the Google sign-in and its return when Google is enabled.
- Stop when:
  - a change would alter `/auth/confirm`, an action's validation or neutral result, RLS, a table or a column;
  - a return-path case passes that G1 rejects;
  - the proxy would change an existing destination or query rule;
  - `/privacy` or `/terms` wording would need to change;
  - a design change outside §1.4 is needed (G12).
- Rollback: revert the PR. The cookies are short-lived (return path) or harmless when unread (last method), there is no data migration, and nothing is irreversible.
